# Component visuals

**Spec version:** `1.0.0-draft` (see [Overview](index.md))

This document defines the **component visual recipe**: a renderer-neutral description of how a component looks, bound to design tokens. A recipe lets tooling produce SVG, PNG, and Figma output, plus anatomy and spec overlays, from one source. It is not tied to Figma, React, or any other platform.

Status: **draft / RFC**. The schema is [`component-visual.schema.json`](../schemas/component-visual.schema.json). A pilot recipe lives at `packages/design-data/visuals/action-button.json`.

## Goals and non-goals

**Goals**

* One data source drives three views of a component: a variant × state matrix (usage), anatomy callouts, and token-labeled measurements (specs).
* Every geometric or paint value is token-bound, so overlays can name the token behind each measurement.
* Output targets are plural: SVG first, then PNG, then Figma.

**Non-goals**

* Pixel parity with every platform implementation. Recipes describe the Spectrum design spec, not a browser's rendering of it.
* Replacing component declarations. Options, states, slots and anatomy stay in [component format](component-format.md).
* Describing interaction, motion or accessibility behavior.

## Layers

| Layer                 | Owns                                                                      | Where                                  |
| --------------------- | ------------------------------------------------------------------------- | -------------------------------------- |
| Component declaration | Options, states, slots, anatomy names                                     | `components/<name>.json`               |
| **Visual recipe**     | Part tree, layout, shape, paint, text, token bindings                     | `visuals/<name>.json` (this spec)      |
| Render request        | Which component, option values, states and modes to draw; matrices        | Tool input (not stored in the dataset) |
| Scene graph           | Resolved rects, paths, text, groups, measurements with part and token ids | Renderer output; backends consume it   |

**NORMATIVE:** A recipe **MUST** name exactly one component through `component`, and that component **MUST** be declared. *Planned Layer 2 rule; not yet enforced.*

**NORMATIVE:** Every key of `parts` **MUST** be a declared anatomy part of the component. *Planned Layer 2 rule; not yet enforced.* Recipes therefore require components to declare anatomy.

**Floating parts.** A part with `floating` is not a child of any part: it is a top-level part drawn beside one side of the root (or at a fraction of a part, see **Position at a fraction**), for an overlay, a tip or a loupe that sits outside the root's box. It is a `box` that either binds `width` and `height` (both positive) and is a leaf, or hosts `children`. **NORMATIVE:** `side` is the root edge it sits against (`top`, `bottom`, `start` = left, `end` = right; logical sides are left-to-right in this engine). `offset` is the gap from that edge in px, default 0; a positive value moves it away from the root and a negative one overlaps the root. `align` places it along the edge: `start`, `center` (default) or `end` of the root's extent on that axis. `crossOffset` shifts it along the edge in px (positive is right or down), default 0. A floating part is solved after the root and never changes the root's layout: no flow, stack, padding or child sees it. It is present when its `visibleWhen` (or its anatomy part's `presentWhen`, e.g. `options: {"isOpen": true}`) holds. It draws after the root and its children, so it is on top, and floating parts draw in part-id order. A floating part with `children` is a subtree: it is laid out as the root of its own scene (so it takes the same props as a root: `direction`, `padding`, `gap`, `width`, `height`, `fill`, `shadow`, and so on, and its children flow or stack as in the root), and its size is the size that layout gives its box (a `width` or `height` it binds fixes that side). The subtree is then moved so that its box sits at the anchor, and its nodes draw in layout order after the root. A floating part inside a floating subtree is not possible: a floating part with `side` is anchored to the root only (one with `position` to the part named by `of`). A `width`, `height`, `offset` or `crossOffset` that is not finite or is beyond 2000px, a non-positive size, and a size that does not resolve, is skipped with a diagnostic; an `offset` or `crossOffset` that is declared but does not resolve is taken as 0 with a diagnostic. A `component` part may also be floating with a `side` (a slider's field label above its track): the nested recipe is solved as for a flowed component part and placed beside the root edge by its own root size, which may be zero wide (a label with no text draws nothing). Floating parts of a nested (`component`) recipe are not drawn: the host drops them with a diagnostic. SPEC-112 checks the declaration.

**Position at a fraction.** Instead of `side`, `floating.position` places the part at a fraction of a part's box, for a slider handle, a color handle on a gradient or a fill that grows with a value. `position` has `of` (a non-floating part, default the root) and `x` and/or `y`, each an axis `{ value, min, max, from, invert, length }`. `value`, `min`, `max` and `from` are `{ "option": name }` (a numeric request option) or `{ "value": n }`; `min` defaults to 0 and `max` to 1. **NORMATIVE:** the fraction is `(value - min) / (max - min)`, clamped to 0 through 1, and flipped (`1 - f`) when `invert` is true (a vertical slider). A point axis (the default) puts the part's center at that fraction of the `of` box's length on that axis; `floating.align` `start` puts its start edge there and `end` its end edge. The part's own size never changes layout. An axis left out centers the part on the `of` box. With `length: true` the part's size on that axis is the span between the `from` fraction (default 0, or 1 when `invert`, with `from` flipped by `invert` too) and the value's fraction, starting at the lower one, so a slider fill is `{ "value": { "option": "value" }, "min": { "option": "minValue" }, "max": { "option": "maxValue" }, "length": true }`, and an offset or range fill sets `from`. A length axis binds no `width` (x) or `height` (y), and an empty span draws nothing. `align` here says which edge of the part sits at the point (`start` puts the part's start edge there), unlike with `side`, where it aligns the part along the root's edge. An `{ "option": name }` that is unset is the start (fraction 0, or 1 when `invert`) with no diagnostic, like a slider with no value (`defaultValue ?? minValue` in React Aria); a value that is present but not a number, not finite, a range that is empty or too wide to subtract (`max <= min`, or `max - min` beyond the float range) is taken as fraction 0 with a diagnostic; a fraction outside 0 through 1 is clamped with a diagnostic. The part may extend past the `of` box, and the scene grows to hold it (see **Scene bounds**). A 2D position (color area) gives both `x` and `y`. An axis may instead be a list of entries, each an axis with an optional `when` (as a conditional value source): the best matching entry is the axis, and with none the axis is left out, so `orientation` can put the value on `x` or on `y` with `invert`. A part of `kind` `component` (a color handle) may carry `position`: the nested recipe is solved as for a flowed component part, its root box is placed as the part would be, and its parts move with it; its size is its own, so it has no `length` axis. A range slider is two handle parts and a fill whose `from` is the lower value's fraction. SPEC-114 checks the declaration, and that every option it reads is a number option of the component.

**Scene bounds.** The scene is the root's box grown by the 8px ring margin on every side, then grown to also hold every floating part and the whole subtree of each (every node of it, with half its stroke) and every drop shadow of every node: the shadow box (offset by `x`, `y`, grown by `spread`) grown by three standard deviations (`1.5 * blur`), the extent the renderers draw. The top-left of the grown scene is the origin, so every node, measurement and press center is shifted by the growth and `viewBox`, `width` and `height` are the grown size. A recipe with no floating part and no shadow reaching past the margin is unchanged.

**Drop shadow.** A `box` (the root too) that binds `shadow` draws one shadow per layer under its fill. The source is `{"shadow": [{"x", "y", "blur", "spread", "color"}, ...]}`: each field is a value source of its own, so a layer binds the atomic `drop-shadow` tokens (`{"token": {"structure": "drop-shadow", "property": "blur", "scaleIndex": "100"}}`). `x`, `y` and `blur` resolve to pixels, `blur` to 0 or more, `spread` is optional (default 0), and `color` resolves to a color whose alpha is the shadow's opacity. **NORMATIVE:** A layer is the box offset by (`x`, `y`) and grown by `spread` on every side (corner radii grow with it, to at least 0), blurred by a Gaussian of standard deviation `blur / 2` (`blur` is the Figma shadow radius and the CSS blur radius), filled with `color`. The first layer is on top, as in CSS. The shadow is drawn before the box's own fill and **MUST NOT** appear inside the box's own shape, so a translucent box shows no shadow through it (CSS `box-shadow` and Figma with "show shadow behind node" off). `blur` is at most 100: a larger value is drawn as 100 with a diagnostic. `color` is a hex, `rgb()`, `rgba()` or `transparent` value; any other color, a layer whose fields do not resolve, a layer whose `x`, `y` or `spread` is not finite or is beyond 1000px (so SVG and PNG size the canvas alike), and a negative `spread` that leaves nothing of the box are skipped with a diagnostic. Node `opacity` dims the shadow with the rest of the component. Shadows are not inset, are not clipped by a parent box, and are never cut by the scene: the scene grows to hold them (see **Scene bounds**). A shadow never moves layout. The node carries `shadow` (`x`, `y`, `blur`, `spread`, `color` per layer) and the shadow's bound tokens as `tokens` entries `shadow<n>.<field>`.

**Path shapes.** A `box` with `path` is drawn as a closed vector shape instead of a rounded rectangle, for a teardrop loupe or a tip with a rounded point. `path.d` is SVG path data of the commands `M L H V C S Q T Z` (absolute or relative); arcs (`A`) are not supported, so use `C` or `Q`. `path.viewBox` is `[width, height]`, the coordinate space of `d`; it defaults to the part's own box, so `d` is then in px. The data is scaled from the `viewBox` to the part's box (`width` and `height`, which the part MUST bind), so one shape serves every size, and the node's top-left is the origin. **NORMATIVE:** every subpath is closed (a missing `Z` is implied, for the stroke too; a relative `m` after an unclosed subpath still starts from where it was written). `path.fillRule` is `nonzero` (default) or `evenodd`. The part's `fill`, `patternFill` and `patternSize` (a checkerboard from the node's top-left, clipped to the shape), `stroke`, `strokeWidth` and `strokeOpacity`, and `shadow` apply to the shape: the stroke is centered on the outline with round joins (it is not inset as on a box, and may reach half its width outside the box), and a shadow is the shape's blurred silhouette offset by `x` and `y` with `spread` not applied, never drawn inside the shape. `cornerRadius` and a gradient fill are ignored on a path (a gradient draws its first stop). A path part may have `children`; they lay out as in a box and are **not** clipped to the shape. A checkerboard inside a teardrop is the path part's own `patternFill`, not a clipped child, so a loupe is a path part with the pattern and a sibling path part for the color. `d` is at most 4096 bytes, 1024 numbers and coordinates of at most 1e6, every coordinate is at most 100000 after scaling, and the part's box is at most 250000 px squared (a path costs a blur and a distance grid per pixel, so a larger one is refused); data that cannot be read is drawn as the plain box with a diagnostic. The node carries `path` (`d` scaled to the node, with every subpath closed, and `even_odd`). SPEC-113 checks the declaration. A path is not clipped by its box: keep `d` inside the `viewBox`, because the stroke bounds and the shadow assume it.

**Image fills.** A `box` with `image` shows a picture, as the cover of a card or dialog, an illustration slot, or an avatar or thumbnail photo, clipped to the box and its corner radii (all four, or each when they differ). `image` has `source`, `fit` and `position`. `source` is `{ "option": name }` (a string option of the request) or `{ "value": "data:image/png;base64,..." }` (a recipe-bundled asset). The engine reads **only** a `data:image/png;base64` URI: it never reads a file or fetches a network URL, so `https:`, `file:` and bare paths are refused, and a host that has an image at a URL or a path embeds it as a data URI first. JPEG, GIF and SVG are not drawn (`image/png` only; an interlaced PNG, `tRNS` transparency, gamma and color profiles are not read either). **NORMATIVE:** a URI is at most 2 MiB (2^21 bytes) and its image at most 4096 pixels on a side and 4 million pixels, checked from the header before any pixel is decoded; the renderer decodes the pixels itself, so SVG, PNG and every consumer of the scene agree on what is drawn. A source that is unset or empty draws the **placeholder** with no diagnostic (so a first-pass recipe can use the part before a request has a picture): a neutral checkerboard of `#d5d5d5` and `#ebebeb` squares of 8 px, drawn as the node's `fill` and `pattern` (replacing the part's own `fill`, `gradient` and `patternFill`), clipped to the corners. A source that is set but cannot be drawn (not a string, not a PNG `data:` URI, over a limit, corrupt or truncated) draws the same placeholder and reports a diagnostic. `fit` is `cover` (default: scales to cover the box, cropping the overflow), `contain` (scales to fit inside, leaving the box's own `fill` showing), `fill` (stretches to the box) or `none` (natural size, one image pixel per px, cropped to the box); an unknown `fit` uses `cover` with a diagnostic. `position` is `[x, y]` from 0 to 1 (default `[0.5, 0.5]`, as CSS `object-position`): 0 puts the image's start edge on the box's start edge and 1 its end edge on the box's end edge. The box's `fill`, `gradient` and `pattern` draw first and the picture over them, then the `stroke`; `children` draw over the picture. Layering is fixed: the box's `fill` or `gradient`, then its `pattern` (checkerboard), then the picture over both (so a transparent or letterboxed picture shows them through), then the `stroke`. JPEG is not read and a host converts to PNG first; a JPEG decoder would be a dependency decision for later. A part with `path` draws no image (SPEC-117). The scene node carries `image` (`href`, `fit`, `position`, `dest`, `size` and `placeholder`), where `dest` is `[x, y, w, h]` of the whole picture relative to the node's top-left, from the fit; the SVG is an `<image>` stretched into `dest` (`preserveAspectRatio="none"`) with a `clip-path` of the box's rounded shape. Scaling is bilinear in the rasterizer. The request, not the recipe, carries the picture, so a recipe binds the source to an option the component declares (a data decision outside this spec). SPEC-117 checks the declaration.

**Progress arc.** A `progress` part draws a ring inside its box, `strokeWidth` thick (a ninth of the diameter when unbound), with the track in `trackColor` and the arc in `color`. The arc starts at 12 o'clock and runs clockwise with round caps, in either text direction. A bound `sweep` is the share of the ring it covers: 0 draws no arc, 1 draws a full ring. An unbound `sweep` draws the fixed quarter-arc frame, so an indeterminate progress circle is a `sweep` list that has no entry for it (like a spinner frame).

**Text height.** A `text` part is as high as its line box: a `lineHeight` ending in `px` is that height, a unitless `lineHeight` multiplies `fontSize`, and with no `lineHeight` it is 1.3 times `fontSize`. A bound `fontFamily` leads the SVG font stack, so a family the viewer lacks falls back to the default stack.

**Text wrapping.** A `text` part that is a direct child of the root and binds `overflow` (inside a row box it is ignored) breaks or truncates its label to fit the width the root leaves it. The prop is named after React Spectrum's `overflowMode` (`wrap` | `truncate`) and, unlike a `wrap` flag, leaves room for other overflow behaviors. With no `overflow`, or with no fixed width (a request `width` or a root `width`), the text hugs on one line and never breaks, as before. The available width is the root's outer width (`max(minWidth, width)`) minus the inline padding, the `gap`s and the width of every other flowed part; a column root gives the text the whole inner width. Several parts with `overflow` share what is left equally. A text part has no width of its own to cap, so the root width is the only constraint: a recipe that needs a narrower label sets a narrower root or a `width` on a box around it.

* `wrap`: greedy line breaking. A line may end after a space or after a hyphen; a hyphen is always a break opportunity, also inside tokens such as `--flag` or `A-1`; trailing spaces do not count toward a line's width. When the padding, gaps and other parts leave no width, the available width is 0: every word takes its own line, and the scene reports the first overflowing word and the generic width diagnostic. Each candidate line is measured with the text table (R2). **NORMATIVE:** A word wider than the available width **MUST NOT** be split: it takes a line of its own and overflows the root, and the scene's `diagnostics` **MUST** say so. Hyphenation, bidirectional and CJK line breaking are not defined.
* `truncate`: one line. When the label is wider than the available width a renderer cuts it and appends `...`, keeping the longest prefix that fits (just `...` when none does).

**NORMATIVE:** A wrapped label is **one scene text node per line**: the same `part`, the same `x`, `y` increasing by the line height, `w` the line's own width and `h` one line height. A part with one line is a single node, so output that does not wrap is unchanged and consumers (SVG, overlays, spec-sheet measurements, the Figma plugin) need no special case. A part that sits beside a wrapped label and is centerd (an icon) centers on the first line, like React Spectrum's `CenterBaseline`. Wrapping depends on the table (R2): a CLI render and a site agree on the lines only when they read the same table.

**Underline.** A `text` part that binds `textDecoration` to `underline` gets a line under its label, in the text's `color`: `underlineThickness` thick, its top edge `underlineOffset` below the baseline. Both default to 1 when unbound; a bound value that is not a number or px value draws 1 and the scene's `diagnostics` say so. Renderers take the baseline as 0.35 x the font size below the center of the line box, so SVG and PNG put the line at the same place whatever the font. The line is therefore approximate: its width is the label's width from the text-metrics table, so a PNG drawn with the real font can end a little before or after the last glyph, and the baseline may sit a pixel off the font's own. A wrapped label draws one line per scene text node, as wide as that line. `textDecoration` is conditional like any property, so a link underlines only on hover or only when it is inline. Any other value draws no line and the scene's `diagnostics` say so. A scene text node carries the line as `underline: {thickness, offset}`.

**Min height.** A root with `minHeight` and no `height` is `max(minHeight, tallest flowed child + block padding)` high. A row root that binds no block padding pads each side by `(minHeight - one line) / 2`, where one line is the tallest flowed child with every label on a single line. So a one-line label gives exactly `minHeight`, and a label that wraps keeps that padding and grows the container by a line height per extra line. A `height` is a fixed height: it wins over `minHeight` (unless larger) and a wrapped label overflows it. A token bound to `minHeight` is reported (`data-tokens`, measurements) as `height`.

**Opacity.** Renderers read `opacity` only on the root part. It dims the whole component as one group (SVG `<g opacity>`), so overlapping parts do not show through each other, the way iOS dims a disabled control. On any other part `opacity` is ignored (SPEC-083).

**Height.** An unset root `height` is the content plus the block padding. A column root is the stacked children. A row root is the tallest flowed child plus the block padding, floored at `minHeight`, and the children sit between the paddings. A row that binds no `minHeight` and no block padding hugs its content. Before layout revision 2 such a row was 32 high whatever its content. An explicit `height` always wins and the block padding then only offsets the children.

**NORMATIVE:** A renderer **MUST** clamp a uniform `cornerRadius` that is larger than half the shorter side of its box to that value, on all four corners, so the corner stays circular (like CSS `border-radius`).

**Row boxes.** A flowed `box` that binds `direction: "row"` lays its `children` out in a row instead of insetting them: `icon`, `text` and `box` children in order, `gap` apart, between its `paddingInlineStart` and `paddingInlineEnd`, centered across (`align` moves them). Without a `width` it is as wide as its children plus padding; without a `height` it is as tall as the tallest child plus its block padding. A `text` child may bind its own padding props, which add to its cell. Only `row` is supported.

**Root width.** A root takes a width only when the design defines one; with no `width` and no `minWidth` it hugs its content (a container with no width record, such as a button group, hugs its copies). The root's outer width is `max(minWidth, width)`, where `width` is the request's `width` if it has one, else the recipe's root `width`, else the content width. With neither a `width` nor a `minWidth` the root hugs its content, as before. Padding stays inside the outer width, so the content area is the outer width minus the inline padding. A request `width` overrides the recipe's `width` but never goes below `minWidth`. **NORMATIVE:** When a fixed width (from the recipe or the request) is smaller than the content, the renderer **MUST NOT** clip or shrink the content: it overflows the root, and the scene's `diagnostics` **MUST** say so. Text with `overflow` fits the width instead (see **Text wrapping**); a word that cannot break still overflows.

**Grow.** In a row (the root, or a row box), parts with `grow` split the space left after the other parts, the `gap`s and the padding, in proportion to their shares. A growing part starts from its content width and gains its share, so with no free space (a hugging root, or content as wide as the row) nothing changes, and a row that is too narrow never shrinks a part. A growing `box` is wider by its share; a growing `text` keeps its own width and starts at the start of its grown space (the text does not move, wrap or truncate). `grow` has no effect in a column or on an `icon`.

**Extra width.** Parts without `grow` do not stretch: in a row root wider than its content they stay grouped and placed by `justify` (centered by default), like a hugging root's content.

**Column stretch.** In a column root, a flowed `box` with no `width` (a divider, a content region, or a row box such as an accordion header) fills the column's inner width. A flowed `box` with no `height` and no children is as tall as its block padding.

**Row boxes.** A row box (a box that binds `direction`, holding `component` or `slot` parts) packs its items at the start of its inner width, or by its own `justify` (`start`, `center`, `end`) when bound; an unbound row box is `start`, unlike the root. `justify` does nothing when an item has `grow`, which takes the free space. An alert dialog's footer, `justify: end`, draws its buttons at the end.

**Corner radii below the root.** A flowed `box` below the root (a stack child, a column or row item) also reads `cornerRadiusStartStart`, `cornerRadiusStartEnd`, `cornerRadiusEndEnd` and `cornerRadiusEndStart`, each falling back to its `cornerRadius`, as the root does; a box nested inside a box still draws one radius.

**Nested boxes.** A flowed `box` child paints itself (`fill`, `stroke`, `strokeWidth`, `cornerRadius`) and may list its own `children`, which are boxes laid out inside it. A nested child is centered across the parent. Along the inline axis its `justify` prop (`start`, `center`, `end`) places it, with an inset equal to the cross-axis gap. A nested child with no `width` or `height` fills the parent. A `cornerRadius` of `0.5` with `relativeTo: "height"` draws a pill, or a circle for a square box. The switch uses this for its track and handle. A nested `icon` is centered on both axes; the checkbox uses this for its checkmark and dash.

**Stack.** A root that binds `direction: "stack"` overlays its flowed children instead of flowing them: every child sits in the root's inner box (the box less its padding), `justify` placing it across and `align` down, centerd by default, and none moves another. There is no `gap`. A child later in `children` is drawn over the earlier ones (z-order is declaration order, also for a `component` part, whose nodes join the scene at that point). With no `width` or `height` the root is as wide and as high as its biggest child plus padding. A `box` child with no `width` fills the inner width, as in a column; a box child needs a `height` of its own. A swatch is a stack of an opacity checkerboard and its fill; a tooltip tip is a stacked sibling of the body. `stack` is a root `direction` only; `row` and `column` are unchanged. A `box` child that binds no `direction` places itself with its own `justify` (across) and `align` (down), instead of the root's; a child that binds neither follows the root. Its `width` may be `{ "value": 0.5, "relativeTo": "parent" }`, a fraction of the root's inner width (a box with no `width` still fills it). Outside a stack a parent-relative `width` is not read (the box is 0 wide). A calendar range band uses these: half a cell wide, at the end of a range's first day and the start of its last, so it meets the day circle's center and ends flush with it.

**Grid.** A root that binds `direction: "grid"` lays its flowed children out in rows of `columns` cells, in children order, row by row. `columns` is a whole number from 1 through 100, a recipe literal (`{"value": 7}`) or a `dimension` option; a repeated part's copies are the cells at its place in `children`, so a month of days is a repeat of a day part, and a table is a repeat of a cell part with a fixed column count (header cells first). A slot part, `component` part or `text` part is one cell each. **NORMATIVE:** a column is as wide as its widest cell and a row as tall as its tallest, `columnGap` and `rowGap` (default `gap`, then 0) apart; the grid is as wide as its columns and gaps and as high as its rows and gaps, plus the root's padding, unless `width` or `height` fixes the root. Cells start at the root's inner top-left corner; `justify` places a cell's content across its column and `align` down its row (`start`, `center` default, `end`), so a day or a table cell sits where the design puts it and no content is stretched. A `box` cell with no `width` fills its column. A short last row leaves its cells at the row's start. `columns` that is not a whole number from 1 through 100 is clamped (a fraction floored, a value below 1 or missing taken as 1, one above 100 taken as 100) and the scene says so; a negative `columnGap` or `rowGap` is taken as 0 with a diagnostic; a grid with no cells is as large as its padding and the scene says "grid has no cells". A repeat draws at most 2000 copies; further entries are dropped with a diagnostic. A grid is a root layout: the root, a repeated part, or any `box` that is a child of one (see **Subtrees**); `columns`, `columnGap` and `rowGap` are read only there. There are no spans and no per-column widths: give a cell a `width` (every cell of a column), or let the widest set it. The gap token is not measured in a grid. SPEC-116 checks the declaration.

**Two strokes.** A box has a `stroke` (the outer one, drawn inside its bounds). A root may also bind `innerStroke`, `innerStrokeWidth` and `innerStrokeOpacity`: a second border that starts where the outer one ends (inset by the root's `strokeWidth`) and is drawn over the children as a `ring` node `<root>.inner-border`. Nothing is drawn unless `innerStrokeWidth` is above 0 and `innerStroke` resolves; corners must be uniform. The records for both strokes belong to one part and property (for example `color` of `attribute: border`) and are told apart by `scope.options.position`, `inner` or `outer`: the recipe binds `stroke` with the plain selector and `innerStroke` with `position: "inner"` (see **Stroke position** under value sources). A box that is not the root draws a second stroke with a `ring` part and `inside`.

**Dashed and per-side strokes.** A root or `box` part with a `stroke` and a `strokeWidth` may bind five more props, all optional, so a recipe that binds none of them draws exactly what it did before. `strokeDash` is the dash length in px and makes the stroke dashed; `strokeGap` is the gap in px (default: the dash length). Both MUST be positive numbers. `strokeCap` is `butt` (default, flat dash ends) or `round`; it only matters on a dashed stroke. `strokeSides` is a space-separated list of `top`, `end`, `bottom`, `start`, or `all` (default) or `none`, and the stroke is drawn only on the listed sides. Like the per-corner radii, `start` is the left side and `end` the right side in both text directions. **NORMATIVE:** the stroke is the same band as the plain border, inside the box, with the corner arcs of the part's radii. A corner arc is drawn only when both sides that meet there are listed, so a side stops at the tangent of an arc it does not draw. A square corner (radius 0) next to a side that is not listed is not inset: the side runs on to the outer edge of the box, so the side of a box that touches it continues into it. Joins inside a run are round. The dash pattern starts at the beginning of each run, a run being the listed sides and corners that join (going clockwise from the top), and flows round corners. `strokeDashAnchor` is `box` (default) or `scene`. With `scene`, each straight side starts its pattern at its own coordinate in the scene (x for the top and bottom, y for the left and right, always counted in the positive direction) and each corner arc starts its own, so the dashes of boxes that touch line up: a band drawn per cell, with the top and bottom sides listed, shows one outline. The order of `strokeSides` words does not matter and `none` among other words adds nothing. With `scene`, a corner arc restarts the pattern at its own start (so the dashes may not continue exactly where a side meets an arc, only at pill ends); with `box` the pattern flows through the arc. An unlisted side, a `strokeSides` of `all` and an unset `strokeDash` leave the plain border. A value that cannot be read (a dash or gap that is not a positive number, a cap or anchor or side that is not one of the keywords) is ignored with a diagnostic, and that prop draws as unset. A stroke style is ignored on a `path` part (whose stroke is centered on its outline) and on a part that draws no stroke. On a root with `strokeOver` the border ring takes the style. The scene node carries `stroke_style` (`dash` as `[dash, gap]`, `round_cap`, `sides` as `[top, right, bottom, left]`, `scene_anchor`; each present only when set) and the SVG draws the stroke as one `<path>` per run with `stroke-dasharray`, `stroke-dashoffset` and `stroke-linecap`, so the rasterizer and the SVG agree on the sides, corners and dashes (the rasterizer cuts the flattened centerline by the same pattern). SPEC-121 checks the declaration.

### Nested recipes

A part of kind `component` draws another component's recipe inside this one. The recipe part names no component: it reads it from the host's anatomy part of the same key, whose `component` field names the component to draw ([Anatomy format: Another component as a part](anatomy-format.md#another-component-as-a-part)). A recipe part with a `component` property is a Layer 1 error, and a `component` part whose anatomy part has no `component` is a SPEC-089 error. For example an icon-only action button and a switch in an accordion item's header:

```json
"action": {
  "kind": "component",
  "sizeMap": { "s": "s", "m": "m", "l": "l", "xl": "xl" },
  "with": { "hideLabel": true, "isDisabled": { "option": "isDisabled" } }
}
```

* **Options.** `with` sets options of the nested component. A value is a literal, or `{"option": name}`, which reads the host's option of that name from the render request (its default when unset) and is skipped when the host has no value for it. A third form, `{"option": name, "map": {"<host value>": "<nested value>"}}`, reads the host's option and picks the nested value through the map; keys are the host value as a string (`"true"`/`"false"` for a boolean). A text field's help text is `{"option": "isError", "map": {"true": "negative", "false": "neutral"}}`. SPEC-089 requires the host option to exist, every key to be a value of it and every mapped value to be valid for the nested option. A host value with no key is not an error: the nested option keeps its default and the scene's `diagnostics` say so. The key is `with`, not `options`: `options` means a condition everywhere else in a recipe. A nested option that is not listed keeps the nested component's default. **Label.** `with.label` is not an option: it is the nested request's `label`, the text its `content: true` text parts draw, measured and wrapped like any label. It is a string literal or `{"option": name}` naming a string host option (a `map` works too); a slot fill's `options.label` sets it the same way. SPEC-089 requires a string value and does not look for a nested option named `label`. When the host's `label` option is not a string, it is a presence flag (`true` when the request has a label and no `label` option, `false` when the request label is empty or the option is `false`): `true` passes the request's own `label` to the nested part, `false` leaves it empty. A string option still wins. When `with.label` is absent, or the host option is unset, the nested label is empty and draws no text, as before. It is how a group of radios gives each item its own text. The nested part gets no other label, no `icon` override and no `width`; those request fields, and the request's interaction states, apply to the host only. `textMetrics` and the mode (`colorScheme`, `scale`) are the host's, so the nested text is measured with the same table.
* **Inheriting the host's box.** A nested root draws at its own size. A `component` part that is a flowed child of the root can instead list `inherit`: `width` and `height` are the host root's inner size (its outer size, `max(minWidth, width)` or the request's, less padding), `cornerRadius` the host root's corner radius. The value replaces the nested root's own binding for that property (a nested `minWidth` still applies). It is how a nested divider spans an item, or a nested checkerboard fills a rounded thumbnail. A value the host root does not fix (a hugging width, no height or radius) is not inherited and the scene's `diagnostics` say so; inside a row box or group nothing is inherited. A recipe with no `inherit` draws exactly as before.
* **Size.** `sizeMap` maps each host size to a nested size, because the scales differ (an accordion has `s`, `m`, `l`, `xl`; an action button also has `xs`). It is resolved when the host variant is compiled.
* **Binding.** The nested recipe binds its own relationships and tokens. The host binds only what is the host's: the `gap` of the row that holds the nested parts, the host's padding, and so on. A literal in `with` needs a reason (a fixed design choice such as icon-only), like any literal.
* **Layout.** A `component` part is a flowed child of the root, a child of a **row box**, or a child of a box inside a row box that binds `direction` (`row` or `column`, a group). Its size is the nested root's solved size; `gap`, `align` and `justify` of the box that holds it apply as for a `box` child. It has no `props` (SPEC-083) and no `grow`. A row box that holds `component` parts and shows none of them (`visibleWhen`) is not laid out at all, so an optional slot leaves no gap. A `component` part anywhere else is not drawn and the scene reports it.
* **Nodes.** The nested recipe is solved on its own and its nodes are appended to the scene, translated into place. **NORMATIVE:** the nested root's node keeps the host part's id (`action`); every other node is `<id>.<part>` (`action.icon`). Recipe part ids never contain a dot. So a consumer that looks nodes up by anatomy part name (the explorer's Anatomy view, spec-sheet markers, overlays) sees the nested component as one part, and a consumer that draws every node (SVG, the Figma plugin) draws it whole. Measurements, press and opacity of the nested scene are not carried; its diagnostics are, prefixed with the part id.
* **States.** The host's `hover`, `down` and `keyboard-focus` do not reach the nested part: it renders in its default state. An option-driven state works through the nested component's own options (`isDisabled`, `isSelected`) when `with` binds them.
* **Limits.** A recipe **MUST NOT** nest itself, directly or through other recipes (cycle), and nesting is at most two levels deep (host, nested, nested in nested). SPEC-089 checks both; the compiler refuses to compile either.
* **Compiled shape.** A compiled `component` part carries `nested` (the nested variant as `CompiledVariant::to_value` writes it: `root`, `optionDefaults`, `parts`, `drawings`) and `nestedSize`. Every other part of a compiled recipe is unchanged, so a reader that does not know the kind sees an unknown part and ignores it. A backend with one variant document (the slim WASM `Engine`) needs nothing else.
* **Platforms.** The nested recipe is looked up through the active platform's component aliases, as the renderer does everywhere: under `--platform`, a nested `button` draws `button-ios` if the platform aliases it. The `sizeMap` must then map into the platform recipe's `sizeScale`, or the compile fails, except that a platform recipe with a single `sizeScale` entry (a system control such as `switch-ios`) serves every host size. SPEC-089 checks the graph it is given.

### Slot parts

A `slot` part draws the **fills** a render request puts in one of the component's slots ([Slots](component-format.md#slots)). The slot is the one of the component whose `part` is this recipe part (not a collection slot), so the recipe names neither the slot nor what it accepts. The request carries the fills as `slots`: `{"<slot name>": [{"component": "<name>", "options": {...}}]}`. A component's slot `demo` ([Slot demo](component-format.md#slot-demo)) is a ready-made list of such fills for showing the component with content. Each fill is drawn through the nested-component path (see [Nested recipes](#nested-recipes)): `sizeMap` chooses its size from the host's, and the part's `with` gives default options (a literal or a host binding, as for a `component` part) applied to each accepted component that declares the option, while a fill's own `options` win.

```json
"actions": {
  "kind": "slot",
  "sizeMap": { "s": "s", "m": "m", "l": "l", "xl": "xl" },
  "with": { "hideLabel": true, "isDisabled": { "option": "isDisabled" } },
  "props": { "direction": { "value": "row" }, "align": { "value": "center" } }
}
```

* **Layout.** A `slot` part is a child of a row box or of the root (a flowed part of a row or column root). Its fills are laid out in request order along `direction` (`row`, the default, or `column`), with `align` (on the cross axis: `start`, `center`, `end`) and `gap` of the slot part's own `props`. A column slot is as wide as its widest fill and as tall as the fills plus the gaps, and stays one item of its row box; a `placeholder` keeps its own size in either direction. Set `direction: column` for a vertical list (radio group, tabs, menu); a slot directly under the root is one flowed block, spaced by the root's `gap`; it reads no other prop (SPEC-083) and has no `children`. A slot with no fills is not laid out, so an optional slot leaves no gap. A repeated part draws the same fills in every copy.
* **Nodes.** The part itself is a `box` node with the slot part's id, as wide and as tall as its fills. Fill *n* (from 1) is a nested component with the id `<id>-<n>`, and its inner nodes are `<id>-<n>.<part>`.
* **Placeholder.** A slot part **MAY** declare `placeholder`: `{ "width", "height", "reason" }`. When the slot has no fills the part draws an empty frame of that size instead of nothing. The size is a recipe literal because it is the size of an empty drop target, which no token describes; `reason` (REQUIRED) says so, as for any literal.
* **Request keys are slot names, not part ids.** A component whose slot is named `default` with part `options` takes `{"default": [...]}`; `{"options": [...]}` matches nothing. A `slots` key that is no slot name of a slot part in the recipe is reported as a scene diagnostic (naming the slots that have a part, and the slot when the key is its part id), and the render does not fail.
* **Constraints are diagnostics.** The slot's `acceptsOnly` and `max` ([Slots](component-format.md#slots)) are enforced by the renderer as scene `diagnostics`, never as a failure: a fill whose component is not in `accepts` while `acceptsOnly` is `true`, a fill for which there is no embedded recipe (a component outside `accepts`), and every fill past `max` are not drawn, and the scene says which. A slot's `min` is not checked at render time.
* **Compiled shape.** A compiled `slot` part carries `slot` (the slot's name), `acceptsOnly`, `max` when set, and `fills`: an object from each accepted component's name to `{nested, nestedSize, with}`, where `with` is the part's `with`, which a nested solve applies only for the options that component declares. A fill of a component the slot does not accept has no entry. The compiled recipe does not depend on the request's `slots`.
* **Validation.** SPEC-108.

### Repeated parts

A collection component (an accordion's items, a tab list's tabs, a button group's buttons) is a container whose child is drawn several times. The **component** says which part repeats and from which option, in a `collection` slot ([Slots](component-format.md#slots)); the **container** says only how an entry is drawn, with `repeat`, because it is the part that knows its children repeat. The repeated child does not know it is repeated. A recipe says so with `repeat` on the root:

```json
"container": {
  "kind": "box",
  "children": ["accordion-item"],
  "repeat": {
    "slot": "default",
    "label": "label",
    "with": { "isOpen": "isExpanded", "content": "content" }
  }
}
```

with the component declaring `"slots": [{ "name": "default", "part": "accordion-item", "collection": "items" }]`.

* **`slot`.** The name of one of the component's slots that declares `collection`. That slot's `part` is the repeated part: an anatomy child of the part that declares `repeat` (listed in its `contains`), a direct child (in `children`) of it in the recipe, and never the root. Its `collection` is the array option; each entry that is an object is one copy of the part. The recipe does not repeat either fact. A part declares at most one repeating child. The root declares `repeat`, and so may a part that another `repeat` draws (see **Nested repeats**) or a `box` that is a child of one (see **Subtrees**), so one tree can hold several repeats, each in its own box (SPEC-060, SPEC-116).
* **`label`.** The entry field that holds the copy's label (the request `label`).
* **`with`.** Maps a component option to the entry field that sets it for that copy. A field the entry does not have leaves the option at the request's value, then the component default. The option may be a string option that a `text` part reads with `text.option`, so an entry can carry more copy than its label: an accordion maps `"content": "content"`, and its `content` part (`kind` `text`, `text.option` `content`, `visibleWhen` `{ "options": { "content": true } }`) draws the entry's content only while it is set and the item is open.
* **Cascade.** Every copy is solved as its own request: the container's size, mode, states and other options reach each copy, and an entry's fields override them. **NORMATIVE:** `part` and the parts inside it are those of one copy; `repeat` adds no parts. Each copy is laid out as a root (it may be a column box, with its own padding and fill), then placed as a flowed child of the container.
* **Layout.** The copies flow in array order along the container's `direction`, `gap` apart, with the container's `padding`, `align`, `justify`, `fill` and `stroke` as for any flowed child. A container takes a width only when the design defines one (a `width` or `minWidth` record on the container); otherwise it hugs its contents. **NORMATIVE:** In a **column**, a container with a fixed width (its `width`, or a request `width`) makes every copy fill its inner width. A hugging column container makes every copy as wide as the widest copy, or as the container's `minWidth` less padding when that is larger (a second solve at that width when the first widths differ). In a **row**, copies keep their own widths and the container is their sum plus the gaps. A request `width` stands for the parent the component sits in, so "fill the parent" is a request width.
* **Nodes.** **NORMATIVE:** The root node of copy *n* (counting from 1 over the entries that are drawn, so a skipped entry does not take a number) is `<part>-<n>` and every other node of it is `<part>-<n>.<inner>` (a `strokeOver` border of the copy is `<part>-<n>.border`). **A single copy** (one entry, or no entries, which draws one copy with the request's own label and options) keeps plain ids: the part's id and its inner parts' ids. The first copy keeps its measurements; the container takes its own opacity, else the first copy's; the scene has no press. Diagnostics of a copy are prefixed with its id.
* **No entries.** When the request does not set the option, or it is empty, one copy is drawn. Entries that are not objects are skipped; when none is an object one copy is drawn and the scene's `diagnostics` say so.
* **Validation.** SPEC-060 checks that `slot` names a slot with `part` and `collection`, that the declaring part is the anatomy parent and the recipe parent of the slot's part, and that it is the root. SPEC-104 checks the slot (the part and the array option exist, and the parent hosts at most one collection slot). SPEC-066 counts the slot's option as used and warns when a `with` key is not a declared option, or when `label` or a `with` field is not a property of the option's item schema. SPEC-083 reads the repeated part with the root's props, because it is solved as a root.

#### Nested repeats

A repeated part may declare `repeat` of its own child, so a tree draws a list of nodes whose children are lists of nodes. The inner `repeat` reads its collection from the copy's options: the outer `with` maps the inner collection option to the entry field that holds the children (`"with": {"children": "children"}`), so each level is one part, one collection slot and one entry field. **NORMATIVE:** a repeat inside a copy that has no entries (the option unset, empty or with no object) draws **no** copy, unlike the outermost repeat, so a leaf has no phantom child. A level's indent is that part's own padding (the recipe has a part per level); the level is its part, so no condition on the level is needed. Repeats nest at most 6 deep: a deeper one is not drawn and the scene says so (SPEC-116 flags the recipe). Position conditions inside a copy are those of the innermost repeat the part is in.

#### Subtrees

A flowed `box` child of the root (or of a repeated part or another subtree) that binds `direction: "grid"` or declares `repeat` is laid out as the root of its own scene, with the host's request, states and options, and joins the parent's flow as one block; its nodes keep their own ids (`weekdays`, `wd0`, `day-1`). So a calendar is a column root of a title, a weekday grid box and a day grid box that repeats `day`, and a table is a column root of a header grid box and a body grid box that each repeat their own cell. Each such box has its own tracks: **NORMATIVE:** columns do not align across two grids, so give cells a `width`, or use one flat repeat in one grid (header cells first). A grid or repeating box inside a plain box, or inside a row box, is not laid out as a subtree (SPEC-116). SPEC-116 skips this placement check when no component catalog is loaded (`validate-dataset`), since the repeated parts come from the component's slots; `validate` with `--components-path` runs it. Subtrees count in the scene budget and the nesting limit below.

**Limits.** A scene draws at most 5000 repeated copies and subtrees in all, however they nest (the 2000 per repeat limit multiplies when repeats nest): later ones are not drawn and the scene says so. Repeats, grids and subtrees nest at most 6 deep. Time grows with the copies drawn.

#### Position conditions

`when.position` (and `visibleWhen.position`) lists the positions at which a conditional entry applies, the way `when.options` lists allowed values: a position or an array of positions. The positions are `first`, `middle`, `last` and `only`.

* **Presence of the repeated part** (its anatomy `presentWhen`) and its `visibleWhen.position` are checked per copy, against that copy's own options (`with` applied) and its position among all the entries. A copy that fails is not drawn and takes no number, as for a skipped entry; the positions of the parts inside the copies that are drawn then count the drawn copies.
* **Evaluated per copy.** The position is that of the repeated copy being drawn, and holds for the repeated part and every part inside it. With *n* drawn copies, copy 1 is `first`, copy *n* is `last` and the ones between are `middle`; a single copy (one entry, no entries, or one entry that is an object) is `only`, and is neither `first` nor `last`. "Not last" is `["first", "middle"]`.
* **Specificity.** A matched `position` counts as one satisfied condition, like an option.
* **Outside a repeated copy** a `position` condition never matches.
* **Relationships.** A relationship record pins the same positions with `scope.itemPosition` ([relationship-format.md](relationship-format.md#derived-item-position)); a recipe's relationship binding then picks the record for the copy being drawn.
* **Row position.** A repeat inside a `grid` also sets `when.rowPosition`, the copy's place in its grid row, with the same four values. **NORMATIVE:** copy *i* (0-based, among the drawn copies, *n* in all) is in column `i mod columns`; it is `first` when that column is the first or it is the first copy, `last` when that column is the last or it is the last copy, `only` when both, otherwise `middle`. It holds for the repeated part and every part inside it, counts as one satisfied condition, and never matches outside a repeat in a grid. A calendar caps a range band with it at the ends of a week row. **Known limits:** `columns` counts at most 100, as the grid lays out; a repeat that is not in a grid keeps the place of the grid copy around it; `rowPosition` is a reserved request option name, so a request option of that name is overwritten inside a grid repeat and not meaningful elsewhere; a calendar's first and last day of the month are not row edges (leading blank cells are copies), so a range running into day 1 mid-week is square there.
* **Validation.** SPEC-061 requires every value of `position` and `rowPosition` to be one of the four positions, and either to appear only on the repeated part or a part inside it.

### Icons

An `icon` part names the icon it draws from the dataset's `icons/` catalog ([`icon-set.schema.json`](../schemas/icon-set.schema.json)):

```json
"disclosure-icon": { "kind": "icon", "icon": { "set": "ui", "name": "chevron" }, "props": { ... } }
```

| Field      | Type    | Description                                                                                                                                            |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `set`      | enum    | `ui` (component glyphs such as `chevron`, `checkmark`, `dash`, one drawing per size) or `workflow` (content icons such as `add`, one 20 px drawing).   |
| `name`     | string  | Icon id in that set. SPEC-085 checks it exists.                                                                                                        |
| `content`  | boolean | The icon is content, like a label: the recipe's icon is a default that a render request may replace. Default `false` (the icon is part of the design). |
| `optional` | boolean | With `content`, a render request may also remove the icon. Default `false`.                                                                            |

A `chevron` points to the end; the `rotation` prop turns it (90 when an accordion item is open).

**Content icons.** A render request **MAY** carry `icon`, either `{"set", "name"}` or `"none"`. It applies to every part whose `icon` has `content: true`, the way `label` replaces the text of the recipe's label. `{"set", "name"}` replaces the part's icon. `"none"` removes the part from the layout as if its `visibleWhen` did not hold; it is allowed only on a part with `optional: true`, and on any other part the renderer **MUST** keep the recipe's icon and emit a diagnostic. A request icon that is not in the catalog draws the placeholder with a diagnostic. Parts without `content` ignore the request's `icon`. The button's icon is `content` and `optional` (a label-only button), the badge's is `content` only, because its `icon` option already hides it. Command-line and API spellings of the override (`--icon workflow:edit`, `--icon none`) belong to the tools, not to this format.

**Choosing a drawing.** A `workflow` icon has one drawing, scaled to the part box. A `ui` icon has one drawing per scale index, and the renderer **MUST** choose its scale like this:

1. The token bound to the part's `width` (else `height`) gives it: the token name's `scaleIndex`, else its `size` key (`xs` 50, `s` 75, `m` 100, `l` 200, `xl` 300, `xxl` 400, the scale of `workflow-icon-medium` and its siblings).
2. Otherwise (a literal size, an inline relationship value or a token whose name has neither field), the recipe's `sizeScale` entry for the request's `size`.
3. Otherwise 100.

The drawing at that scale is used; when the icon has none, the renderer **MUST** draw the nearest available scale (the larger one on a tie). SPEC-086 warns when a recipe falls back, since another size's drawing has different stroke weights and proportions. The scale is chosen once per size and mode, from the bindings the part has with no states and default options, so a state or option never changes the drawing. A renderer **MAY** make this choice when it compiles the recipe.

**Drawing.** The renderer scales the icon's `viewBox` uniformly to fit the part box, centered, applies `rotation` about the box center, and fills every path, honoring its `fillRule`, with the part's resolved `color`. Icon data carries no color. A part box that is not square leaves the icon at the smaller side, so an icon part's `width` and `height` are the icon's size, not the size of the shape it draws.

An icon with no drawing (no such set or icon in the catalog, or no catalog) **MUST** draw a placeholder plus in the part box and emit a diagnostic naming the set, the icon and the request's size.

### Value sources

A property value is either one **value source** or an ordered list of **conditional value sources**. A value source is exactly one of:

* `{"value": <literal>}`: a literal. Use only for geometry that no token describes (e.g. a glyph path).
* `{"token": {<name-object fields>}}`: a token selected by name-object fields, resolved with the [cascade](cascade.md).
* `{"relationship": {"property": "...", "context": "..."}}`: a token chosen through the component's [relationships](relationship-format.md). `property` and `context` match the relationship's `scope.property` and `context`. A selector may instead name the record by its structured identity: `attribute` (the record's `scope.attribute`), `part` (its `scope.part`) and `between` (its `scope.between`) in place of `context`. It **MUST** name at least one of `part` and `between`, and it matches every record whose given fields equal the record's; a field it leaves out is not compared. The selector **MUST** name exactly one identity, the combination of `attribute`, `part` and `between` among the records it matches (SPEC-062). Because a field left out is not compared, a selector that omits `attribute` names several identities when the records differ by attribute, and SPEC-062 reports it. A part is the owner of the record's token concept, not necessarily the part that binds it: the handle of a switch can bind a record whose part is `track`. A selector with `context` and any of `attribute`, `part` or `between` is invalid. **Stroke position.** A selector **MAY** add `position` (`inner` or `outer`, default `outer`), with `context` or with the structured fields. A record whose `scope.options.position` is `inner` or `outer` serves only the selector with that position; a record with no such pin (or another value, such as a type style's `top`) serves both. Where records of both kinds share every other pin, the one pinned to the selector's position replaces the unpinned one, so the two strokes' colors do not collide. `position` does not change a selector's identity (SPEC-062). **Root part.** While a component migrates, a record that describes the component as a whole names an explicit root part, and a selector for it names that part. Once the component reaches the structured-identity level (computed by the status report), the root part is implicit and omitted from records and selectors; that cut-over is not yet in force.
* `{"option": "<name>"}`: a color the request carries in the string option `<name>`, for a value no token holds (a swatch's preview color). Only solid colors are read: `#rgb`, `#rgba`, `#rrggbb`, `#rrggbbaa`, `rgb()`, `rgba()` and `transparent`. **NORMATIVE:** A value that is not one of these or a `linear-gradient()` (an image, a name, a number) **MUST** be dropped with a diagnostic, and a fully transparent one (alpha 0) **MUST** be dropped without one; the option then counts as unset, so `visibleWhen` and `when` conditions on it (`false` for unset, `true` for set) and the part's unset look apply. The renderer draws the color over whatever is behind it: it draws no backdrop for a color with alpha below 1. A `linear-gradient()` is read as a gradient fill on a box (see `gradient` below); on any other prop it is not a drawable color. Only the `deg` angle and the `to <side or corner>` forms are read, with `<color> [<percentage>]` stops; a stop with no position sits evenly between its neighbors. Any other form (a `radial-gradient()`, a stop that is not a solid color, positions that go back) is dropped as above.
* `{"gradient": {"from": [x, y], "to": [x, y], "stops": [{"color": <source>, "offset": <source>}, ...]}}`: a linear gradient on a `box` `fill`. `from` and `to` are the ends of the gradient line in the box's own unit space, `[0, 0]` its top-left corner and `[1, 1]` the bottom-right (defaults `[0, 0]` and `[1, 1]`), as Figma gradient handles give them, so a gradient that stops short of the corners can be drawn. Each stop's `color` and `offset` is a value source of its own (usually a relationship, so the gradient-stop tokens drive it); a `color` resolves to a color and an `offset` to a number from 0 through 1. **NORMATIVE:** There **MUST** be at least two stops, every stop **MUST** resolve and offsets **MUST NOT** decrease; otherwise the renderer draws the plain `fill` and reports a diagnostic. A scene node with a gradient carries it in `gradient` (`from`, `to` and `stops` with `color`, `offset` and the bound `token`), and its `fill` is the first stop's color, for a consumer that draws solid fills only. The renderer draws the gradient in the box's pixel space with the line's ends at those points, so its bands are square to the line whatever the box's shape (a CSS `linear-gradient()` is read the same way, with the line as long as the box is along the angle).
* `{"gradient": {"from": [x, y], "to": [x, y], "ramp": {"color": {"option": name}, "channel": <input>, "space": <input>, "z": <input>}}}`: a linear gradient whose stops the engine computes from a color and a channel, as React Spectrum draws a color slider's track and a color area, so a recipe binds no color strings for the ramp. `from` and `to` are as above, so the direction (left to right, right to left, bottom to top for a vertical slider) is the recipe's, and a gradient may be a list of `when` entries. `color` is `{ "option": name }`, a string option holding the current color (`#rgb`, `#rgba`, `#rrggbb`, `#rrggbbaa`, `rgb()`, `rgba()`, `hsl()`, `hsla()`, `hsb()`, `hsba()`, `transparent`). `channel`, `space` and `z` are each `{ "option": name }` or `{ "value": "<name>" }`; `channel` is `hue`, `saturation`, `lightness`, `brightness`, `red`, `green`, `blue` or `alpha`, and `space` is `hsl`, `hsb` or `rgb`. **NORMATIVE:** without `z` the ramp is a slider track for `channel`: the color is converted to the working space (`space`, else the color's own space when it has the channel, else the channel's: hsl for `hue`, `saturation`, `lightness` and `alpha`, hsb for `brightness`, rgb for `red`, `green` and `blue`), the channel takes values across its range (hue 0 to 360, saturation, lightness and brightness 0 to 100, red, green and blue 0 to 255, alpha 0 to 1), the other channels keep the color's values and the alpha is 1, as React Spectrum's `getDisplayColor` gives. The `hue` track is the exception: it is always the full-saturation rainbow (saturation 100% and lightness 50%), whatever the color. Only the `alpha` track keeps the color's own alpha, and runs from it at alpha 0 to it at alpha 1. `hue` has seven stops 60 degrees apart (offsets 0, 1/6 ... 1), `lightness` three (0, 50 and 100, offsets 0, 0.5 and 1, the middle so that the hue shows) and every other channel two (its minimum and maximum, offsets 0 and 1); `alpha` runs from the color at alpha 0 to the color at alpha 1 and the part draws no checkerboard itself (a recipe stacks the ramp over a part with `patternFill`, as React Spectrum does). Stops are `#rrggbb`, or `rgba(r, g, b, a)` when not opaque (written as `stop-color` like any gradient stop), rounded to 8 bits; the renderer blends between them in sRGB, not premultiplied, so the engine does not interpolate. With `z` the ramp is one layer of a color area, and `channel` is the layer's channel while `z` is held at its value in the color (`space` is `hsl` or `hsb`, the color's own space when it is one, else `hsl`). The layers are those of React Spectrum's `useColorAreaGradient` and the recipe stacks them in the space's channel order from the last (on top) to the first, with, when `z` is `hue`, a layer with `channel` equal to `z` (a solid of `hsl(z, 100%, 50%)` or `hsb(z, 100%, 100%)`) at the bottom: `hue` is seven stops of the base color (saturation 100% and lightness 50% or brightness 100%, with `z` at its value) with the hue varied, `saturation` the base color at saturation 0 fading to transparent, `lightness` black fading to transparent in the first half and transparent to white in the second (stops at offsets 0, 0.5, 0.5, 1) and `brightness` black fading to transparent. A faded stop keeps its color at alpha 0, so the blend matches a premultiplied one. The x channel runs along `from` to `to` horizontally and the y channel vertically from the bottom, as React Spectrum's `to right` and `to top`. Layers of an area stack by part id, as floating parts are drawn in id order (name them `a-...`, `b-...`). A `ramp` that is not drawable draws the plain `fill` with a diagnostic: an unknown channel or space, a channel the space lacks, a missing `channel`, `space` or `z`, an area layer for the fixed channel (unless it is `hue`), and an area in `rgb` (React Spectrum blends its three channel layers with `screen`, which the renderer has no equivalent of; an rgb area stays unsupported, and would need a per-pixel ramp source, not a blend mode). An unset `color` option, or one that is not a readable color, draws the ramp for `hsl(0, 100%, 50%)` with a diagnostic. SPEC-115 checks the declaration. A scene node carries the computed `gradient` like any other, so SVG, PNG, WASM, the TUI and the spec sheets draw it with no change; a conic ramp for a color wheel is not drawn, but its hue stops are the `hue` track.
* `{"dimension": "<name>"}`: a size in pixels the request carries in the numeric option `<name>`, for an extent no token holds (an opacity checkerboard's `verticalSize` and `horizontalSize`). An unset option uses the component's declared default. **NORMATIVE:** A value that is not a positive number is dropped with a diagnostic and the property counts as unset. Prefer a relationship when a token holds the value. A `dimension` source **MAY** add `fallback`, one more value source (usually a `relationship`): **NORMATIVE:** when the option is unset or not a positive number the renderer resolves `fallback` in its place, so a size the host may set falls back to the component's default token, as in `{"dimension": "width", "fallback": {"relationship": {...}}}`. A `fallback` with no `dimension` is invalid. A renderer that does not read `fallback` treats the size as unset. **Known limits:** `fallback` is one source, not a `when` list (the schema rejects a list), and a spec sheet does not read a relationship inside a `fallback`.
* `{"fraction": {"value": "<option>", "min": "<option>", "max": "<option>"}}`: a share of a range, `(value - min) / (max - min)` clamped to 0 through 1, read from the numeric options it names. `min` defaults to 0 and `max` to 1 when the option is unset or not named; an unset `value` is 0, and an empty range is 0. The result is relative to the parent (see below). A progress bar's fill width is one. As text, the fraction is a whole-number percentage, rounded, so it can read `1%` while the fill is a fraction of a pixel.

Selector strings **MAY** contain `{size}` (the request's `size` option value, e.g. `m`), `{sizeIndex}` (that size's entry in `sizeScale`) and `{<option>}` for any other option the component declares (for example `{style}`). A `{<option>}` placeholder expands to each value the option declares, and a candidate found for one value applies only when the request's option equals that value, so one selector serves every value. A brace pair whose content is not a plain identifier (letters and digits) is literal text. A scalar `token` selector value matches an array-valued name field that contains it (e.g. `"state": "disabled"` matches `["disabled"]`).

**NORMATIVE:** A relationship may pin component options in its `scope.options` (a value, or an array of values that match when any listed value matches). For a `relationship` selector the renderer **MUST** keep only the matching relationships whose pinned options all match the request, and **MUST** prefer the ones that pin the most options. A relationship that pins no options is the default: it applies only when no relationship that pins options matches. Keys that are not declared options of the component, and the reserved keys `state`, `scale` and `colorScheme`, are not pinned options. A relationship's `scope.options.state` adds states to those of the token it binds, so a hover color that is a plain palette token can still be selected by state. This lets the component data, not the recipe, say which token applies under which options (for example a badge label is white by default, black for the light variants, and gray for subtle).

**NORMATIVE:** `token` and `relationship` selectors yield a set of candidate tokens. The renderer **MUST** narrow the candidates with the request's mode context (for example `colorScheme`, `scale`) using the [cascade](cascade.md), and **MUST** report a diagnostic if zero or more than one candidate remains.

**NORMATIVE:** When several candidates remain after narrowing, a renderer **MAY** fall back to the candidate whose token name has the fewest name fields (the most general token), and only then report a diagnostic for candidates that still tie with different tokens. A recipe **SHOULD NOT** depend on this fallback: pin `variant`, `anatomy` or another name field in the selector instead.

A conditional entry is a value source plus `when`. A condition has optional `options` (option name → value, or array of values), `states` (state names that must all be active) and `modes` (mode-set name → mode) and `position` (see [Position conditions](#position-conditions)). An array matches when any listed value matches, and counts as one condition.

**NORMATIVE:** When several entries match a request, the renderer **MUST** choose the one with the most conditions (options + states + modes). Ties go to the later entry in document order. An entry without `when` is the default. An entry **MAY** set an integer `priority` (default 0); a higher priority wins before condition count is compared. Use it for states that override every other combination, such as `disabled`.

**NORMATIVE:** On `width` and `height` of a nested box, `relativeTo: "parent"` makes the numeric value a ratio of the parent box's inner size on the same axis, and a `fraction` source is always relative to the parent. A renderer **MUST** treat a ratio of 0 as a zero-size box. `relativeTo: "parent"` has no effect elsewhere.

An entry on `cornerRadius` **MAY** set `relativeTo: "height"`, making its numeric value a ratio of the container height (a pill is `0.5`). An entry on the root's `minWidth` **MAY** set it too: the value is then a multiple of the root's one-line height (`minHeight`, else `height`), so a minimum width such as `2.25` times the height reads from a multiplier token. A `stroke` on a `box` is drawn inside its bounds, so `strokeWidth` does not change the layout size.

**NORMATIVE:** A renderer **MUST NOT** substitute a literal for a value source it cannot resolve. It **MUST** emit a diagnostic naming the part, property and selector, and omit that property.

### Derived contexts

Some relationship contexts describe a value the layout already implies. The vertical spacing from a container's edge to its label is `(height - line height) / 2` for a content-centerd container, so a recipe that binds the container's height and centers its content gets that spacing for free. Binding the spacing token as well would fix the value where the design source derives it (and break it when the label wraps or the scale changes). A recipe lists such a context under `derived` rather than binding it:

```json
"derived": [
  {
    "context": "Spacing (top/bottom edge to label)",
    "property": "component-top-to-text-{sizeIndex}",
    "part": "label",
    "from": "(height - label.lineHeight) / 2"
  }
]
```

| Field      | Description                                                                                                                               |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `context`  | The relationship `context` that is derived.                                                                                               |
| `property` | The relationship `scope.property` of the records it covers, as in a `relationship` selector.                                              |
| `part`     | The part the spacing leads to. Spec sheets put the marker there.                                                                          |
| `edge`     | `top` (default) or `bottom`: the container edge the spacing starts from.                                                                  |
| `from`     | The formula. Only `(height - <part>.lineHeight) / 2` and `(height - <part>.height) / 2` exist; `height` is the container's solved height. |

**NORMATIVE:** A renderer **MUST NOT** read a `derived` entry; it changes no scene. `<part>.lineHeight` is one line's height of the part, so the formula holds when the label wraps: the padding stays that value and the container grows (see **Min height**); tooling **MUST** solve with a label that does not wrap. Tooling reads a `derived` entry for two things. A spec sheet shows the context with a highlight on `part`, a marker and a measurement of the formula's value over the solved scene, labeled as derived from height. SPEC-087 compares, for every size and scale, the token the context's relationship gives with the formula's value over the solved scene. The comparison is a warning: a context whose relationship resolves no token is reported once, and a disagreement means the token data or the recipe's layout is wrong, never that the recipe binds the token. A control that is centerd on the first label line (a checkbox or switch control) declares the label's formula, since the shared token is the space above the label line.

**NORMATIVE:** A renderer **MUST NOT** read a platform manifest's `extensions/deviations/` ([manifest.md](manifest.md#extensionsdeviations)); like `derived`, it changes no scene. Overrides and platform recipes change what is drawn; a deviation only says where a platform cannot match it.

### Interim: relationship `context` strings

**Structured selectors.** A selector can name `attribute`, `part` and `between` instead of `context` (see value sources). New recipe bindings **SHOULD** use them: the number of `context` selectors per recipe is held at a baseline that can fall but not rise, and a recipe with no baseline entry starts at zero (`tests/context_selector_baseline.rs`). SPEC-062 reports a structured selector that names more than one identity, where the identity is `(property, attribute, part, between)`. It is an error for a component whose identities are all distinct (no two records of one identity differ in `context`, and no recipe selector matches more than one identity) and stays a baselined warning for the others.

Relationship `context` is free text today (for example `Background (selected, emphasized)`). Recipes bind to those strings so the pilot can ship without changing relationship data. This is brittle: a reworded context breaks a recipe, and SPEC-062 reports a `relationship` selector that matches no relationship. **RECOMMENDED:** a follow-up adds structured `options` to relationships so recipes can select by option and state instead of by label.

A `floating` part is a top-level `box` that is neither the root nor a child, has no `placement`, and has `children` or binds `width` and `height`                                                                                                                                                                                                                                                        |   |
| SPEC-113 | Error. A `path` part is a `box` that binds `width` and `height`, with path data the engine can draw (see **Path shapes**)                                                                                                                                                                                                                                                                                       |   |
| SPEC-121 | Error. A literal `strokeDash` or `strokeGap` is a positive number, `strokeCap` is `butt` or `round`, `strokeDashAnchor` is `box` or `scene`, and `strokeSides` lists only `top`, `end`, `bottom`, `start`, `all` or `none` (see **Dashed and per-side strokes**)                                                                                                                                                |   |

SPEC-066 to SPEC-070 are warnings, so `validate` stays green while recipes are migrated. A ratchet keeps the debt from growing: `sdk/core/tests/recipe_lint_baseline.rs` compares each (rule, recipe) warning count with `sdk/core/tests/fixtures/recipe-lint-baseline.json`. A new warning fails the test, an improvement must lower the baseline, and a recipe that is not in the baseline must have none.

## Type styles

A `text` part **MAY** bind `typeStyle` to a [type-style record](relationship-format.md#type-style-records) instead of binding each font axis. The binding is a `relationship` selector like any other, for example `"typeStyle": { "relationship": { "property": "type-style", "part": "label" } }`, and takes the same conditional forms as other props (options, states).

* **Expansion.** **NORMATIVE:** The record's `$ref` **MUST** be a typography composite. The renderer unpacks it for the request's `scale` (the composite's inner `{legacy-name}` aliases resolve by mode) and uses its `fontFamily`, `fontSize`, `fontWeight` and `lineHeight` as if the part had bound those props to the inner tokens. The composite's `letterSpacing` is not read. The record is chosen like any relationship record: by options and states, and by the composite's own `name.size` against the request's size, unless the record pins `options.size`.
* **Precedence.** **NORMATIVE:** A font prop the part binds itself (`fontFamily`, `fontSize`, `fontWeight`, `lineHeight`) wins over the type style for that axis, and the type style still supplies the others. This is a rule of the recipe: each axis is resolved as its own binding, and the token cascade never mixes a composite's sub-values with other tokens, so it does not conflict with the atomic-composite rule in [Token format](token-format.md#composite-value-types). A recipe keeps a per-axis binding for what a composite does not carry or must differ (a CJK line height, a line height that is a multiple of the font size, a part with no matching composite).
* **Reporting.** A `token` reference in the scene names the composite (`component-m-bold`) and its `chain` starts with the inner token (`font-size-100`). A `typeStyle` that cannot be used adds a diagnostic and leaves the axis unset, as an unresolved binding does: `typeStyle: '<label>' is not a typography composite` when the `$ref` is another kind of token, and `typeStyle: <composite>.<axis> '{<alias>}' not found` when an inner alias has no token for the request's mode, or `typeStyle: composite has no such axis` when the composite lacks that axis. Existing diagnostics are unchanged.
* **Scenes.** Moving a part from per-axis bindings to a type style keeps the geometry, font size, font weight and line height when the composite carries the same values. The `font-family` attribute (the composite binds a family, so it leads the stack) and the `data-tokens` labels change; this is a data-only snapshot change (see [Layout revision](#layout-revision)).

## Spec sheet sections

A generated spec sheet (`component-spec-sheet.schema.json`) carries an optional top-level `sections` array beside `pages`. It holds the non-measurement template sections in order: `anatomy`, `usage`, `states`, `accessibility`, `decision-log`, `how-to-use`, `feedback`. Each section has `key`, `title` and `blocks`. A block is `prose` (paragraphs, bullets, optional `do` and `dont`), `table` (`columns`, rows of text cells) or `placeholder` (a `hint` saying what goes here and that it is filled in by hand). Generators emit every section; those the data cannot back yet hold one placeholder block. Renderers **MUST** ignore `sections` they do not know.

## Layout revision

The solver is shared by the CLI, WASM, MCP and TUI, and a solver change can move existing recipes without a recipe change. The renderer carries an integer **layout revision** (`LAYOUT_REVISION` in `sdk/core/src/visual.rs`) and the dataset declares the one it was authored against as `layoutRevision` in `dataset.json` ([Dataset layout](dataset-layout.md)). **SHOULD:** a renderer warns, outside the scene `diagnostics`, when the two differ; a dataset without the field is revision 0. **NORMATIVE for this repository:** a change to the solver or to layout semantics that alters the committed recipe snapshots bumps both numbers in the same change. A data-only change to the snapshots (the same geometry and resolved values, for example the `font-family` attribute or the `data-tokens` labels after a recipe moves to a type style) does not bump `layoutRevision` and does not by itself raise `requires.cli`.

## Platform-owned recipes

Implemented for `render`, `site` and the Rust core (see [Proposal 014](../../../docs/proposals/014-platform-owned-visual-recipes.md)). `render` and `site` load the foundation recipes into the graph, then apply the platform's `extensions/visuals/` over them, and look recipes up through `componentAliases`.

* **Location.** **NORMATIVE (when implemented):** A platform recipe is `extensions/visuals/<component>.json`, one recipe per file, in the platform's extensions directory (honoring `extensionsDir`, see [Manifest](manifest.md#extensions-directory)). The file name **MUST** equal `component`. It validates against the same recipe schema as a foundation recipe, so promoting or demoting it is a file move ([Artifact moves](artifact-moves.md)).
* **Precedence.** A platform recipe **replaces** the foundation recipe of the same component name as a whole file. There is no layering. A foundation recipe stays the default for platforms that have none. A replaced recipe is a copy that can drift; SPEC-080 reports the pair.
* **Resolution.** A recipe's selectors resolve against the platform-merged graph (the manifest's tokens, relationships, components and anatomy). A recipe replaces only the look; anatomy stays neutral, so a recipe may use only the parts the platform-merged component declares (SPEC-060).
* **Validation.** `validate --platform <id>` runs SPEC-060 to SPEC-074 and SPEC-083 over platform-owned recipes against the platform-merged graph, plus SPEC-079 (every request in the grid renders). SPEC-076 keeps its foundation comparison and covers only foundation recipes the platform did not replace.

## Authoring conventions

These are the conventions the lints above enforce, plus the decisions made while adding the first five recipes. Follow them in a new recipe; a change to an existing recipe that breaks one needs a reason.

1. **Bind through relationships.** A recipe takes a value from the component's relationships by default (SPEC-067). Use a `token` selector only when no relationship covers the value, and a literal only for layout keywords, `transparent`, zero, ratio radii or geometry no token describes (SPEC-068). If the token you need is missing, file the gap; do not hide it behind a literal. Put option-dependent choices in the relationships, not in the recipe: pin `scope.options` on the relationship records (a default with no options, overrides that pin them) and bind the role once, so a variant added later is a data change. **Exception: platform-owned components.** A recipe for a component that a platform manifest declares (for example `button-ios`) MAY bind platform tokens directly with `token` selectors, because the platform's own code binds tokens by name and has no relationship layer. This applies to platform-owned components only; foundation components stay relationship-first. SPEC-062 and, for platform recipes, SPEC-079 keep checking that every selected token resolves. Watch the recipe size: the mapping from option to token then lives in the recipe, so name the platform's tokens so that selectors can template the option values, and measure the recipe's line count (see [Proposal 014](../../../docs/proposals/014-platform-owned-visual-recipes.md)).
2. **Bind current tokens.** Do not bind a deprecated token (SPEC-069; SPEC-058 covers relationships). When the only token is deprecated, bind it and record the gap, so the lint keeps showing it.
3. **Selection is an option, not a state.** Model "selected" as the `isSelected` option and scope relationships with `options.isSelected: true`. The renderer treats `isSelected` as the `selected` state and `isDisabled` as `disabled` when choosing between tokens that carry a state.
4. **Cover the component.** Every option and state the component declares either changes the recipe or is listed in `notVisual` (SPEC-066). `notVisual` records a deliberate absence, for example `isReadOnly` (it only suppresses hover and press), or the button's `icon` option, which names a workflow icon but does not yet choose the content icon a request draws (p6ga.17.4 decides how the two relate).
5. **Press scales the part the design scales.** Set `pressTarget` to the part the design source scales when pressed: the checkbox scales its `box` (with its mark), the switch scales its `handle`. Parts nested inside the target scale with it, and the label does not.
6. **Priorities.** Disabled overrides interaction states with `priority: 10` (11 where a more specific disabled case must win). Error uses `priority: 5`.
7. **Relationship contexts are the design token group label,** with no `S1` or `S2` prefix, and the same label names the same concept in every component (for example `Control (disabled)`).
8. **Name the focus ring part alike** across recipes (SPEC-070).
9. **Prove a change.** `sdk/core/tests/recipe_snapshots.rs` renders every valid option, state, size, color scheme and scale combination of every recipe and compares a hash per option set with `tests/fixtures/recipe-snapshots.json`. It also fails on any render diagnostic. After a recipe, relationship, token or renderer change, review the option sets it reports with `design-data render`, then regenerate with `UPDATE_RECIPE_SNAPSHOTS=1`. A new recipe is covered automatically.

New recipes **MUST** be free of SPEC-066 to SPEC-070 warnings. Existing recipes are held at their baseline until they are migrated.

## Render request and scene graph

A render request is tool input, not dataset content: `{component, options, states, modes, label, icon, width, slots, overlays}`. `slots` fills the component's slots with other components (see [Slot parts](#slot-parts)). `label` replaces the label text, `icon` the content icon (see [Icons](#icons)) and `width` (px, optional) is the demo width of the root (see **Root width**); empty means the recipe's own width. A **matrix** is a list of requests plus a layout (rows × columns by option or state).

The scene graph is the contract between resolution and output:

* Nodes: `group`, `rect` (with corner radii), `path`, `text`, `ring`.
* Every node carries `part` (anatomy name) and, for each token-bound property, `tokens` (property → token name or uuid and resolved value).
* Measurements (height, padding, gap, radius) are recorded as dimension annotations with their token. Overlay backends draw dimension lines and callouts from these; recipes do not author overlays.

**NORMATIVE:** A backend **MUST** produce the same scene graph input for the same request and dataset version (deterministic output).

### Compiled recipes

A build step **MAY** pre-resolve every `token` and `relationship` binding per `size|colorScheme|scale` into a ranked list of candidates (`{value, token, states}`), so a renderer needs no token graph. Only state-dependent selection remains at render time: take the first candidate whose `states` all apply, else the first. The layout solver that consumes compiled recipes is written once, in Rust, and every surface runs that code: the CLI natively, and the browser (`design-data site`) as a slim WASM build. A backend **MUST NOT** reimplement layout or text measurement; it draws the scene the solver returns.

A compiled recipe **MUST NOT** depend on the request's `icon`: the request icon is applied when the scene is solved. For this a compiled content icon part (`icon.content: true`) carries `iconChoices`, an object mapping `set:name` to the key in the recipe's `drawings` of that icon's drawing at the part's scale (an icon with no usable drawing is absent), so a backend with one precompiled variant and no icon catalog can honor the request icon with the rules in [Icons](#icons). `iconChoices` is absent when the build had no icon catalog. Backends that predate `iconChoices` ignore it, and the existing `drawing`, `drawingMiss` and `drawings` fields are unchanged.

## Backend and tooling decisions (research outcomes)

These record the research behind this draft and are not normative.

**R1 — Playground (Domino) fit: reference only for now.** Domino models component *instances* (`componentType`, props, `items`/`itemsOrder`, slots). It has no geometry, paint, layout or token-binding concepts, no JSON Schema for the node envelope, and no document-format versioning. Its `0react-spectrum/s2` schemas are generated from React Spectrum, and prop names (`isQuiet`, `isDisabled`, `staticColor`) mostly match ours. The repository is private (`"private": true`; MIT metadata but no LICENSE file), so a public spec must not depend on its schemas. Its Figma plugin maps Figma → Domino, the opposite of our Figma output. Decision: keep recipes independent. A render request can later be converted to or from a Domino instance by an adapter, because option names align. Revisit when Domino publishes a versioned envelope schema.

**R2 — Text measurement: approximate metrics with Source Sans 3.** Adobe Clean is proprietary and cannot be redistributed in this repository. Source Sans 3 (SIL OFL) is the open fallback. Renderers ship a width table for the fallback font and emit SVG `<text>` with the stack `'Adobe Clean Spectrum VF', adobe-clean-spectrum-vf, 'Adobe Clean', 'Source Sans 3', sans-serif`, so viewers with Adobe Clean Spectrum VF installed or loaded see it. The variable font's installed name has spaces, and browsers match family names exactly, so the hyphenated Typekit name alone misses it and the browser falls through to its generic sans-serif, which is about 18 % wider. A family name that is not a valid CSS identifier sequence (`Source Sans 3`: a word starting with a digit) **MUST** be quoted, because one unquoted invalid name makes the browser drop the whole `font-family` list and render serif; a family bound by a recipe is emitted quoted and ahead of this stack. Overlay positions use the measured width and may differ slightly from the viewer's font. Line breaks (see **Text wrapping**) come from the same table, so two renderers agree on the lines only when they read the same table; the CLI and a site that ship the same table agree. SVG output maps font-weight names from tokens (`medium`, `bold`, and so on) to numeric weights. Exact shaping (rustybuzz or similar) is deferred until a licensed-font story exists. Outlining text to paths is **not** used for SVG, since it would require the proprietary font. **RECOMMENDED:** a page that embeds the SVG inline loads Adobe Clean through its own web font (for example the Typekit kit the docs site uses, family `adobe-clean-spectrum-vf`). Standalone `.svg` files, SVG used as an `<img>` or CSS background, and rasterized PNG output cannot load web fonts. They use the installed font or fall back to Source Sans 3, so exports **MAY** look slightly different from the live view. Outlining text at export time with a locally licensed font is a possible later option.

**R3 — Layout: minimal flex first.** The pilot box model needs row direction, centering, gap, padding and one absolutely placed child. A purpose-built layout of that size avoids a dependency and keeps WASM small. It exists once, in the Rust solver; browsers load it as WASM rather than a second implementation. Wrapping a label is a greedy breaker in the solver (see **Text wrapping**), and a nested recipe is the solver run on a second recipe (see [Nested recipes](#nested-recipes)); neither is a layout engine. Revisit `taffy` when text-field (stacked label and help text) is piloted.

**R4 — Icons.** Icon geometry is SVG path data in the dataset's `icons/` catalog, imported from React Spectrum S2 (UI icons at every size, a few workflow icons). Recipes reference it by set and name ([Icons](#icons)); they hold no path data.

**R5 — Figma.** The Figma backend consumes the scene graph and emits node JSON for a plugin to create frames bound to Figma Variables by token id, reusing the Variable mapping in `sdk/plugins/figma`. It requires no Figma-specific data in recipes.

## Open questions

* **Structured relationships.** Newer relationships already carry a `part` field and structured `options` (for example `state`, `size`, `scale`). Recipes should prefer them over `context` strings as more components adopt them; action-button's relationships still use labels only.

* **Deprecated tokens.** The pilot's icon sizes bind to `workflow-icon-size-*` tokens that validation (SPEC-058) reports as deprecated in 14.5.0 with no `replacedBy`. The recipe follows the relationships until a replacement is mapped.

* **Switch.** The switch recipe covers default, hover, down, keyboard-focus, and disabled, across selected and emphasized. Its track and handle colors come from relationships added for it, taken from the Figma token spec. They await design sign-off.

* **Pilot coverage.** The action-button recipe covers default, hover, down, focus, disabled, and static black/white. Quiet, selected, and emphasized fills are not yet authored.

* Should render requests (presets, matrices) be stored in the dataset for the Hub site, or stay tool input?

* Which gaps in component-scoped tokens block recipes beyond the pilot? action-button binds only through relationships; many components have none.

* Does `visibleWhen` need boolean composition (any/not), or are single conditions enough?
