# Behavior contract

**Spec version:** `1.0.0-draft` (see [Overview](index.md))

This document defines the **behavior contract**: one file per component, `behaviors/<component>.json`, that states what a component does as data. It names which options are state, what each intent does to them, which facets the appearance layer may read, each part's role and focus model, and a set of conformance vectors. The contract never mentions tokens or dimensions; a recipe may read only the facets it publishes.

Status: **draft**. [Proposal 022](../../../docs/proposals/022-behavior-contract.md) is the source for the format, its worked examples (Switch, Checkbox) and its open questions. This page states what the schema and the validator enforce today. The schema is [`behavior.schema.json`](../schemas/behavior.schema.json); shared base contracts use [`behavior-pattern.schema.json`](../schemas/behavior-pattern.schema.json). The components with a contract are the files in `behaviors/` (the pressed and toggled controls, Radio group, the display components Progress bar, Progress circle, In-field progress circle and Meter, the groups Button group, Swatch group, Checkbox group and Avatar group, and Tooltip); their vectors are in `conformance/behavior/`.

## The file

| Field         | Type      | Description                                                                                               |
| ------------- | --------- | --------------------------------------------------------------------------------------------------------- |
| `component`   | string    | The component declaration this contract describes. **Required.**                                          |
| `extends`     | string\[] | Shared base contracts: names of files in `behaviors/patterns/`, for example `interactive` (see Patterns). |
| `state`       | string\[] | Option ids the contract owns. The option stays the source; the contract does not redeclare it.            |
| `facets`      | object    | Facet id to its derivation from `state` options (see Facets).                                             |
| `parts`       | object    | Anatomy part name to `role`, `focus`, `press`, `handles`, `wcag`.                                         |
| `transitions` | object\[] | Guarded table: `on` (intent), `needs`, `guard`, `do`, `emit`.                                             |
| `semantics`   | object    | Part, then facet, to the accessibility state it exposes (`ariaState`, `map`).                             |
| `range`       | object    | The options a single-thumb value range reads and writes, its page and its mirror (see Ranges).            |
| `wcag`        | object\[] | WCAG 2.x criteria that apply to the whole contract. Also allowed on a facet and on a part.                |
| `vectors`     | object\[] | Conformance vectors: `start`, `steps`, `expect`, optional `needs`.                                        |

### Facets

A facet is a named, finite-valued view of state. [`registry/facets.json`](registry.md#behavior-contract-registries) lists each facet id and its values, and whether it comes from a state group (`state-group`, derived from options the component declares) or from the shared `interactive` base (`interaction`: `hovered`, `pressed`, `focusVisible`). An interaction facet also carries `stateName`, the interaction state name (`states.json`) a recipe resolves against: `hovered` to `hover`, `pressed` to `down`, `focusVisible` to `keyboard-focus`. `states` stays on the component for token identity; the names a recipe resolves against are derived from facets.

A contract declares each state-group facet it uses: `from` names one option or several, and `values` maps each facet value to the option value that selects it. With several sources the values are object matches tried in order (`"order": "first match wins"`). Checkbox keeps `isSelected` and `isIndeterminate` as booleans and derives the tri-state `checked` (`unchecked`, `checked`, `indeterminate`) this way:

```json
"checked": {
  "from": ["isSelected", "isIndeterminate"],
  "values": {
    "indeterminate": { "isIndeterminate": true },
    "checked": { "isIndeterminate": false, "isSelected": true },
    "unchecked": { "isIndeterminate": false, "isSelected": false }
  },
  "order": "first match wins"
}
```

### Intents

A transition is triggered by an **intent**, never a DOM event. The registry [`registry/intents.json`](registry.md#behavior-contract-registries) reuses, unchanged, the vocabularies of the `intents` and `keyboardIntents` arrays of the [`accessibility`](accessibility.md) block: `trigger`, `select`, `navigate`, `expand`, `collapse`, `input`, `choose`, `dismiss` (`intents`) and `activate`, `expand`, `collapse`, `navigate-options`, `navigate-items`, `increment`, `decrement`, `dismiss`, `select-all` (`keyboardIntents`), and the range value intents `increment-page`, `decrement-page`, `set-min` and `set-max`. The registry also holds the **event** intents (`category: event`) that a platform maps a gesture to: `focus` (with `via`: `keyboard`, `pointer` or `programmatic`), `blur`, `press-start`, `press-end`, `press-cancel`, `pointer-enter`, `pointer-leave`, `navigate-next`, `navigate-previous`, `navigate-first`, `navigate-last` and `move`. They exist only in contracts, never in the `accessibility` block. Nothing else is registered.

### Capabilities

A transition or vector may require a capability from [`registry/capabilities.json`](registry.md#behavior-contract-registries): `pointer-hover`, `keyboard`, `assistive-activation`. An implementation on a platform without it neither runs nor fails the vectors that need it, and its facet (`hovered`) never becomes true.

### Parts, transitions, semantics, vectors

* `parts` keys are anatomy part names. `role` is a role from the [accessibility role vocabulary](accessibility.md#role); a component-level role goes on the root or primary part, chosen per component (Switch: `track`, Checkbox: `box`). `focus` is `tab-stop` (in the tab order), `roving` (one peer is the tab stop at a time) or `none`. `press` is the intent a completed press produces. `handles` lists the intents the part handles that **change no state** (`navigate-items`, `increment`): an intent that changes state is a transition instead.
* A `guard` is `{ "facet", "is" }`, or `all`, `any` or `not` of guards. `do` is `{ "toggle": option }` or `{ "set": { option: value } }`, where a value is a literal or `{ "not": guard }`. `emit` names the event raised.
* `semantics` maps state to what assistive technology reads, per part. `ariaState` is the ARIA attribute for web; other platforms map the same state through their own adapter. An entry is keyed by a facet id and has a `map` from facet value to the attribute's value, or is keyed by an option id (listed in `state`) and has `copy: true`: the attribute is the option's value as given, and absent while the option is unset. A `copy` entry may add `absentWhen` (`{ option: value }`, all must hold), which removes the attribute: an indeterminate progress bar has no `aria-valuenow`.
* A vector is a `start` state, `steps` (an `intent`, with `via` for focus, or an `input`), and `expect` entries giving the facets and emitted events after a numbered step. `emit` in an expectation lists the events raised by that step only (`{ "change": { "isSelected": true } }`: the event name and the options it changed, compared exactly). A vector may set `"emitOptions": "listed"` to check only the options it lists: the shared `button` role key vectors use it, so `{ "press": {} }` matches a press that also toggled `isSelected` on Action button. Every other vector is exact. A facet expectation may be a string or a boolean (`focusVisible: true`). An `aria` expectation (`{ "aria-valuenow": "40" }`, `null` for an absent attribute) is read from the contract's `semantics` after that step; an attribute the contract does not expose fails the vector. A vector has at least one step, so a vector that only reads the starting state uses an event intent that does nothing (`blur`). A `move` step also carries `position` (see Ranges). A vector in a contract or a component suite names intents, not keys: Space versus Enter is a platform binding (see Key bindings), not part of a contract. A key-level vector is an `input` step in a bindings suite. A radio-group vector carries `orientation` and, for a right-to-left case, `direction` in `start` (see Radio button and radio group).

### `wcag`

The contract carries the WCAG criteria that `accessibility.wcag` carries today, as `{ criterion, level, title }` entries. Use the level that fits the claim: the whole contract, one facet (for a criterion about a state) or one part.

### Patterns

A shared base contract is a file in `behaviors/patterns/<pattern>.json` ([`behavior-pattern.schema.json`](../schemas/behavior-pattern.schema.json)): a `pattern` id, an optional `description`, `extends`, and the contract fields several components share (`facets`, `parts`, `transitions`, `wcag`). `publishes` lists the registered interaction facets an extending contract may read. A contract reads `hovered`, `pressed` or `focusVisible` only when a pattern it extends publishes it, so the base is data, not code. `interactive` is the first pattern; `toggle` extends it. A pattern that has its own interaction transitions rather than the shared ones lists the facets it sets in `publishes` and need not extend `interactive` (`trigger-reveal`). SPEC-118 warns when `extends` names no pattern, a pattern extends no pattern, or a pattern publishes a facet that is not a registered interaction facet.

#### The toggle pattern

`toggle` (extends `interactive`) is the shared base of a two-state control: Switch and Checkbox extend it. It declares the `checked` (`unchecked`, `checked`), `disabled` and `readOnly` facets from `isSelected`, `isDisabled` and `isReadOnly`, and one `activate` transition: while the control is neither disabled nor read-only it toggles `isSelected` and emits `change`. A pattern has no `state`, so the extending contract lists those three options in its own `state` (SPEC-118 and SPEC-119 warn when it does not). A contract overrides facets and parts by name (its own entry replaces the pattern's, and a derived pattern's replaces the base's). Its own transitions are tried before the pattern's, so a same-intent transition preempts the pattern's only while its guard holds; when it does not, the pattern's transition is tried next. Checkbox overrides `checked` (adds `indeterminate`) and `activate` (also clears `isIndeterminate`, so an indeterminate or both-true checkbox toggles `isSelected` as a native input does, decisions A509 and A510). A read-only control keeps focus, ignores `activate`, and a part may expose it as `aria-readonly` through `semantics`. A read-only control still shows hover and press feedback (the interactive pattern still sets `hovered` and `pressed`; decision A543): only activation is blocked. Switch and Checkbox map `readOnly` `false` and `true` to `aria-readonly` `"false"` and `"true"`; a platform that omits the attribute when false is still conformant, because the map cannot yet say "absent".

#### The press pattern

`press` (extends `interactive`) is the shared base of a control that is pressed and holds no value: Action button, Button and Close button extend it. It declares the `disabled` facet from `isDisabled` and one `activate` transition: while the control is not disabled it emits `press`. A completed press (`press-end` after `press-start`, from the `interactive` pattern) reaches `activate` through the part's `press`, so a press and a keyboard or assistive activation end in the same place. A disabled control takes no focus, press or hover (`blocksInteraction`), so a disabled press never completes. The transition changes no option, so its `do` is `{ "set": {} }`. The extending contract lists `isDisabled` in `state`. A control with `isPending` (Button, Action button) adds the `pending` facet and a first `activate` transition that does nothing while pending, so a pending press raises nothing (decision A550). Action button also has `isSelected` (decision A550): `activate` toggles it, emits `press` with the new `isSelected`, and the part exposes it as `aria-pressed` through `semantics` (facet `selected`). `hasHoldIcon` stays out of the contract. Button has no component of its own selected state, and Close button has neither option.

#### Ranges

A single-thumb value range (slider) is one contract with a `range` block and the `range` pattern (extends `interactive`; decisions A658, A660, A661). `range` names the options: `value` (required), `min`, `max` and `step` (a missing option reads 0, 100 and 1), and sets the `page` (`{ "fraction": 0.1 }`, the default, or `{ "size": n }`) and an optional `mirror` guard. The pattern's transitions answer `increment` and `decrement` (one step), `increment-page` and `decrement-page`, `set-min`, `set-max` and the event intent `move` with the single action `do.adjust`: `{ "by": 1 | -1, "unit": "step" | "page" }` or `{ "to": "min" | "max" | "position" }`. The runner does the arithmetic, so no platform repeats it:

* Snap: the result of a `by` move or a `position` is `min + round((x - min) / step) * step`, with a half rounding away from the minimum, rounded to 10 decimals so `0.1 + 0.2` reads `0.3`, then clamped to `min` and `max`. `to: min` and `to: max` set the bound exactly, even when it is off the step. So `End` sets a maximum that is off the step, while a `move` to position 1 or a step down from it lands on the last lattice point (max 10, step 3: `End` gives 10, a drag to the end gives 9). The quotient is rounded to 9 decimals before it is rounded to a whole step, so an exact decimal half (0.35 with step 0.1) rounds away from the minimum (0.4) whatever the float noise.
* An option that is unset reads the default; one that is set but not a number fails the vector. Limits: values above 1e298 overflow and a step below 1e-10 never moves; both are unsupported.
* Page: a fraction of the span rounded to the step and never below one step, or the fixed `size`.
* Numbers stay whole: `41.0` in a vector or a platform's value is `41`, in options, events and attributes.
* Emit only on change: an adjust that leaves the value as it is raises no event. Otherwise it emits `change` with the new `value`.
* A `move` step carries `position`, the logical position from 0 at the minimum to 1 at the maximum (a vector with a position outside 0 to 1, or a `move` with none, fails). The adapter turns pointer geometry and right-to-left into that position, so `mirror` does not touch it. A pointer drag is `press-start`, any number of `move` steps, then `press-end`; the pattern's own `press-end` raises no `press`, because a range has no press.
* `mirror` is a guard over the contract's own facets: while it holds the runner swaps ArrowLeft and ArrowRight before it looks the key up, as for a collection. A disabled range (`disabled` facet, from `isDisabled`) ignores every value intent.

The options `range` names belong in the contract's `state` (SPEC-119 warns, and the runner's pins check fails, when one does not; SPEC-119 also warns on `do.adjust` with no `range`). Web binds the role `slider`: ArrowRight and ArrowUp `increment`, ArrowLeft and ArrowDown `decrement`, PageUp and PageDown the page intents, Home `set-min`, End `set-max`, all on key down. Left out for now: two thumbs, wrap, a second axis, number formatting, hold to repeat, wheel and Shift steps. Slider, Color slider and Rating are the range contracts. Each has role `slider` on one part (`thumb`; Rating's is `container`), the `arrowOrder` facet from `direction` alone (`rtl` mirrors; `orientation` does not), `aria-valuenow` and, where the component declares them, `aria-valuemin` and `aria-valuemax`; Slider and Color slider also publish `orientation` as `aria-orientation`. Rating has no min or step option, so it reads the defaults 0 and 1, and names a `maxValue` option (component default 5) for its maximum; a drag lands on a whole star (a half rounds up) and a fractional aggregate value snaps to a whole star on the next step. A range's min, max and step come from the options the caller passes: the runner does not apply defaults declared in component data (an unset `maxValue` reads 100), so the caller merges them before it runs a vector or drives the contract. `move` is a slider position (0 at the minimum, 1 at the maximum), not star hit-testing: for Rating an adapter passes the center of the hit star, `(k - 0.5) / maxValue`, because position 0.41 lands on star 2 although it is over star 3. `aria-valuenow` is absent while `value` is unset, so the caller must pass a value (Rating's default is 0). The contracts describe the single-thumb value only, also for a slider with `isRange: true`. The shared key suite `bindings/web/slider.json` runs on all three; two thumbs (`isRange`) and read-only are not modeled. The runner vectors for the pattern itself are in `sdk/core/tests/behavior_vectors.rs`. Number field is a range contract with role `spinbutton` on its `field` part and no `orientation` or `direction`: web binds the role `spinbutton` with ArrowUp and PageUp `increment`, ArrowDown and PageDown `decrement` (a page is one step, so the page intents are unbound), Home `set-min`, End `set-max`, and leaves ArrowLeft and ArrowRight to the caret. Its `in-field-button` part has focus `none`: the stepper buttons are not in the tab order. Number field's `minValue` and `maxValue` have no component default, so an unset bound reads the runner default (0 and 100) and the caller should pass both. The `known limit` vectors pin this, and that an unset `value` reads the minimum (ArrowUp gives min + step, ArrowDown and Home change nothing), as the runner behaves today; the owner may change either, and those vectors then flip on purpose. The shared key suite is `bindings/web/spinbutton.json`; read-only, hold to repeat, wheel, IME and number formatting are not modeled.

#### Radio button and radio group

A contract describes one component, and the state of a contract is options of that component, so a group's peers are not state. The split is:

* **Radio button** (extends `interactive`; `state`: `isSelected`, `isDisabled`) has the part `control` with role `radio` and `focus: roving`. `activate` chooses it (`do: { "choose": "isSelected" }`, emits `change`) while it is not disabled and not already selected, because a radio is never deselected by a press. It has no `navigate-*` transition: moving between radios, and selecting the one the arrow lands on, belong to the group ([Collections](#collections), decisions A540 and A600). `navigate-first` and `navigate-last` are not bound for radio (decision A539), so Home and End do not move selection.
* **Radio group** (`state`: `orientation`, `direction`, `isDisabled`) has the part `container` (role `radiogroup`), `focus: none`, and exposes `aria-orientation` from the `orientation` facet. Its `arrowOrder` facet is the right-to-left rule of decision A542: `mirrored` when the group is horizontal and `direction` is `rtl`, else `natural`. Its `collection` block says how its radios move and choose: single choice, no empty value, wrap, skip a disabled radio, select on move, and swap Left and Right while `arrowOrder` is `mirrored`.
* `direction` (`ltr` or `rtl`) is not an option of any component: it is a property of the environment, registered in [`registry/environment.json`](registry.md#behavior-contract-registries) with its values and its initial value (`ltr`; decision A551). A contract lists it in `state` and a vector sets it in `start`, the way the implementation reads it (React Spectrum S2 reads the locale, Spectrum Web Components the `dir` attribute). SPEC-118 and SPEC-120 accept a registered environment property where an option is expected and warn on an unregistered one or a value the registry does not list; the runner starts a run at the initial value and fails a vector that starts at an unlisted value. `direction` is the only entry; add others only with an owner decision.
* The group's value is not a contract field: it is derived from its items (the indices that are on), and a `change` event of the group lists them. Radio group's part `container` has role `radiogroup`, in the contract and in the `accessibility` block (decision A549). The spec sheet takes `focusable` for Radio button from the block, because `roving` is not derivable.

#### Collections

A group is a collection (decision A599; proposal 022, question 5): a contract with an optional `collection` block describes the group's items without a pattern of its own and without a flat "next enabled peer" state. The group contract carries the traversal and choosing rules; the item contract (a component contract, or an inline one) keeps what one item does. Shape ([`behavior.schema.json`](../schemas/behavior.schema.json), `$defs/collection`):

```json
"collection": {
  "slot": "default",
  "item": "radio-button",
  "choose": { "mode": "single", "allowsEmpty": false },
  "traversal": {
    "wrap": true,
    "skip": { "facet": "disabled", "is": "true" },
    "selectOnMove": true,
    "mirror": { "facet": "arrowOrder", "is": "mirrored" }
  }
}
```

* `slot` is a slot of the component. `item` is the name of a component contract when the slot `accepts` components, or an inline contract (`state`, `facets`, `parts`, `transitions`, `semantics`) when the slot is a `collection: items` slot whose entries are drawn as copies of a part.
* `choose.mode` is `none`, `single` or `multiple`, or `{ "facet": id }`, a group facet whose values are those. `choose.allowsEmpty` is a boolean or a facet reference with the values `true` and `false`. A facet reference lets the group's own option decide, for example a selection mode.
* `traversal`: `wrap` (a boolean) wraps from the last item to the first and back; `skip` is a guard over the **item's** facets and the runner passes over an item it holds for (a disabled item); `first` and `last` (booleans, default false) make `navigate-first` and `navigate-last` move to the first and last item not skipped; `selectOnMove` (a boolean or a facet reference) fires the item's `press` intent on the item the move lands on, so selection follows focus; `mirror` is a guard over the **group's** facets, and while it holds the runner swaps ArrowLeft and ArrowRight before it looks the key up in the bindings, which is how right-to-left reversal stays out of the physical key bindings (principle 12); `focus` optionally overrides the focus model of the item's part (metadata only; the runner does not model focus).
* **`do.choose: <itemOption>`** is a new action for an item transition. In a group it is resolved by the group's `choose`: `single` turns the item on and every other item off, and an item that is already on turns off only when `allowsEmpty` is true; `multiple` toggles the item, but never turns off the last item that is on unless `allowsEmpty`; `none` does nothing. The group then emits **one** event named by the transition's `emit`, `{ change: { <itemOption>: [indices of the items that are on] } }`, and only when the set changed. Outside a group `choose` toggles the option, so a standalone item keeps its own guards (a radio's guard still refuses to turn an already selected radio off).
* An inline item's `semantics` have the shape of the contract's own and read the item's facets: an accordion header exposes `aria-expanded` from `expanded` (decision A623). A collection with no `traversal` declares no navigation: `navigate-*` on its group does nothing (decision A625). Items are addressed by index, in document order. The runner keeps a logical focus index and moves it by index over items the `skip` guard does not hold for; it models no DOM focus.

Vectors for a group add `start.items` (one option set per item, run as the item contract), `start.focused` (default 0), a step `item` (the intent runs on that item), an `input` step (a key resolved through the **group's** role bindings, after `mirror`; with `input.item` it is resolved through the role of the **item** contract's part and the intents run on that item, decision A624), and the expectations `expect.items` (per item, facet values; `null` is an item not checked), `expect.itemAria` (per item, the attributes its `semantics` expose; `null` is an item not checked), `expect.focused` and `expect.emit`. `navigate-*` on the group moves the focus (unless the collection declares no `traversal`, when it does nothing); any other intent on the group runs the group's own machine. Key vectors for the group live with its role (`bindings/web/radiogroup.json`), and the arrow bindings are on the `radiogroup` role, not on `radio`.

The adapter keeps what a vector cannot see: typeahead, the DOM focus technique, scrolling into view, two-dimensional grids, hierarchy (trees) and the propagation of the group's `isDisabled` to its items. The runner does not propagate it either: `navigate-*` on a disabled group still moves the logical focus, and its vector pins only the `disabled` facet. SPEC-118 checks that the slot and item resolve and that a facet reference reads a declared group facet with the right values; SPEC-119 that `skip` and `mirror` read facets of the item and the group, and that `do.choose` names an option in `state`; SPEC-120 that a vector's item options, indices and expected item facets resolve. The runner fails a vector that starts `items` on a contract with no `collection`, a vector whose expectation carries `items` or `focused` but which starts no `items`, and a vector whose start item sets an option the item contract does not list in `state` (or an environment property). SPEC-118 to SPEC-120 run over the contracts' own `vectors`; the separate suite files (`conformance/behavior/*`) are checked by the runner only, and linting them is a follow-up. The runner's start-item check uses the item contract's `state` list (plus environment properties), while SPEC-120 checks against the component's declared options, so a start item option declared on the component but missing from the contract's `state` is accepted by the linter and failed by the runner. Radio group is the first contract with a collection and Accordion the second (an inline item contract, no `traversal` because each header is its own tab stop, a facet `expansion` for the choose mode) and Swatch group the third ([below](#swatch-and-swatch-group)); Tabs, Checkbox group, Button group and Avatar group follow in their own changes.

#### Swatch and swatch group

* **Swatch** (extends `interactive`; `state`: `isSelected`, `isDisabled`) has the part `container` with `focus: tab-stop` and `press: activate`, and no role: its component has no `accessibility.role` and which role it takes inside a group is open (decision A591 left to the owner). `activate` chooses it (`do: { "choose": "isSelected" }`, emits `change`) while it is not disabled. Standing alone it toggles; inside a group the group's `choose` decides.
* **Swatch group** (`state`: `enableSelection`, `selectionMode`, `allowsEmptySelection`) derives the facets `selection` (`none` while `enableSelection` is false, else `multiple` or `single`; first match wins) and `allowsEmpty`. Its `collection` reads both for `choose`, so selection off chooses nothing. Traversal does not wrap, skips a disabled swatch and does not select on move (decision A589 c: Spectrum Web Components and React Spectrum S2 select on activation, not on arrow); `focus: roving` is metadata: it overrides the swatch part's `tab-stop` for items inside the group, so a standalone swatch stays a tab stop (Radio button, which only exists in a group, declares `roving` on its part instead). Space and Enter on a swatch have no web binding (the adapter owns them), because bindings are keyed by role and the swatch has none. The part `container` keeps role `group` (a role that changes with the selection mode is an open question), so the arrow keys have no web binding yet: bindings are by role and `group` is shared with groups that do not move focus. The suite drives `navigate-next` and `navigate-previous` as intents.

#### Interaction transitions

What an event intent does to an interaction facet is pattern data, in the same transition format as a contract. A transition may add `via` (`keyboard`, `pointer` or `programmatic`: it applies only to an event carrying that `via`) and, in `do.set`, name an interaction facet the pattern publishes with `true` or `false`. `do.raise: "press"` fires the `press` intent of the first part that declares one. It carries no `via`, and it is allowed only on a transition for an event intent, so it cannot re-trigger itself (the runner also stops a nest deeper than 8 as a failure). Transitions are tried in order and the first that matches fires; an event that matches none changes nothing, so a platform without the capability a transition `needs` (`pointer-hover`, `keyboard`) never sets that facet. The `interactive` pattern carries:

| `on`                     | Applies when                | `do`                                 |
| ------------------------ | --------------------------- | ------------------------------------ |
| `focus`, `via: keyboard` | the run has `keyboard`      | `set focusVisible: true`             |
| `focus`                  | any other `via`             | `set focusVisible: false`            |
| `blur`                   |                             | `set focusVisible: false`            |
| `press-start`            |                             | `set pressed: true`                  |
| `press-cancel`           |                             | `set pressed: false`                 |
| `press-end`              | `pressed` is `true`         | `set pressed: false`, `raise: press` |
| `press-end`              | otherwise                   | `set pressed: false`                 |
| `pointer-enter`          | the run has `pointer-hover` | `set hovered: true`                  |
| `pointer-leave`          |                             | `set hovered: false`                 |

A `press-end` with no prior `press-start` (or after `press-cancel`, or while a facet's `blocksInteraction` stopped the start) raises no `press`: a press completes only if it began. SPEC-119 warns when `raise` is on a non-event intent, when a contract (or a pattern it extends) raises `press` and no part declares one, and when a `state` option is named like an interaction facet. It also checks a pattern's transitions: registered intents and capabilities, guards reading only facets the pattern declares or publishes (with their values), and `do` setting a published facet only to a boolean. A pattern's `do` may toggle or set an option, because it names no `state`: SPEC-119 checks it against the `state` of each contract that extends the pattern.

#### Display: progress and meter

A component that takes no input but tells the user a value has a contract with no `extends`, no transitions and `focus: none`. Progress bar, Progress circle and In-field progress circle carry role `progressbar` and `wcag` 4.1.2 and 4.1.3; Meter carries role `meter` and 4.1.2. The role goes on `container` for Progress bar and Meter, and on `track` for the two circles, which have no container (the track is the outermost drawn part). `state` lists the value options the component declares (`value`, `minValue`, `maxValue`, and `isIndeterminate` for the progress ones), and `semantics` copies `value`, `minValue` and `maxValue` to `aria-valuenow`, `aria-valuemin` and `aria-valuemax`; on a progress component all three are absent while `isIndeterminate` is `true`, which is how its data words them ("Not applicable when indeterminate"). In-field progress circle declares no value option, so it carries only the part. The vectors read the attributes (`aria`) for a determinate value, a custom range, zero, a fractional value, an unset value and the indeterminate case, and run every event intent through the contract to show none changes anything or raises an event (a contract with no transitions handles only the event intents, so `activate` fails). There is no shared pattern for them: the parts differ by component, and the only shared field would be `wcag`. Progress bar and Meter also copy `valueLabel` to `aria-valuetext` (decision A578; absent while unset, and for Progress bar while indeterminate); Progress circle and In-field progress circle declare no `valueLabel`. Both also copy `label` to `aria-label` (decision A581; `hideLabel` does not matter, and labelledby waits for a way to reference a part); defaults (`minValue` 0, `maxValue` 100) stay in the component's options, so a vector sets them in `start`.

A group component has a contract for the group itself: one part, `container`, with `focus: none` and the role its `accessibility` block declares (`group` for all four; Checkbox group gained it with its contract, after the Radio group precedent). `state` lists the options that carry behavior: `orientation` and `isDisabled` (Button group, Checkbox group), published as the `orientation` and `disabled` facets; the three selection options of Swatch group, which feed its `selection` and `allowsEmpty` facets and its `collection`. Orientation is a facet only: ARIA does not support `aria-orientation` on role `group`. Vectors read the facets and show that no focus, press or pointer event raises an event on the group. The behavior of the items (the buttons, the checkboxes, the swatches) is in the item contracts; whether `isDisabled` reaches the items and whether arrow keys move focus through the group are not declared and stay with the adapter (for Checkbox group the prose and the React Spectrum S2 and Web Components implementations disagree, an open decision, so it carries no navigation). There is no shared `group` pattern: the common fields are `focus: none` and `role: group`, and orientation exists on two of the four.

#### Tooltip

A tooltip is shown by its trigger, so its contract describes the trigger's side of the relationship: the events are the trigger's (and the tooltip's, see hover below), the state is the tooltip's. It extends the `trigger-reveal` pattern (`behaviors/patterns/trigger-reveal.json`), which publishes `hovered` and `focusVisible`, declares the `open` (from `isOpen`) and `disabled` (from `isDisabled`) facets, and holds every transition. The contract lists `isOpen` and `isDisabled` in its `state`, and has one part, `container`, with role `tooltip` and `focus: none` (the tooltip is never focused; WCAG 1.4.13 and 4.1.2). Opening and closing emit `change` with `isOpen`.

| Intent                          | Applies when                    | Does                                                                                      |
| ------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------- |
| `focus`, `via: keyboard`        | closed, run has `keyboard`      | opens; `focusVisible` true; emits `change`                                                |
| `focus`, `via: keyboard`        | already open                    | `focusVisible` true, no event                                                             |
| `focus`, other `via`            |                                 | `focusVisible` false; never opens (pointer or programmatic focus does not show a tooltip) |
| `pointer-enter`                 | closed, run has `pointer-hover` | opens; `hovered` true; emits `change`                                                     |
| `pointer-enter`                 | already open                    | `hovered` true, no event                                                                  |
| `blur`                          | open                            | closes; clears `focusVisible` and `hovered`; emits `change`                               |
| `blur`                          | closed                          | clears `focusVisible` and `hovered`                                                       |
| `pointer-leave`                 | open                            | closes; clears `hovered` and `focusVisible`; emits `change`                               |
| `pointer-leave`                 | closed                          | clears `hovered` and `focusVisible`                                                       |
| `press-start` (trigger pressed) | open                            | closes, clears `hovered` and `focusVisible`; emits `change`                               |
| `press-start`                   | closed                          | clears `hovered` and `focusVisible`                                                       |
| `dismiss`                       | open                            | closes; emits `change`; hover and focus are left as they are                              |

The tooltip closes as soon as either signal ends, whether or not the other still holds it: `pointer-leave` and `blur` each clear both `hovered` and `focusVisible`, as React Spectrum S2 does (`useTooltipTrigger` clears both refs on hover end and on blur). After a close the tooltip reopens only on a new `focus` (keyboard) or `pointer-enter`; keyboard focus that is still on the trigger does not reopen it by itself. Spectrum Web Components keeps it open while the other signal still holds (decision A627 chose the S2 behavior). `disabled` blocks `focus`, `press-start` and `pointer-enter` (`blocksInteraction`), so a disabled tooltip never opens; it can still close (`blur`, `pointer-leave`, `dismiss`) if `isOpen` was set.

**Escape** is a web key binding on the `tooltip` role: `Escape` raises `dismiss` on key down. React Spectrum S2 closes on key down (`useTooltipTrigger`), and so does Spectrum Web Components (`OverlayStack.handleKeydown` closes a hint overlay on Escape key down; `HoverController.handleKeyup` is a redundant second path), so the binding matches both. A DOM adapter listens for it on the document while the tooltip is open, because focus is on the trigger, not on the tooltip. `dismiss` leaves `hovered` and `focusVisible` as they are, so the tooltip does not reopen until a new `focus` or `pointer-enter`; the next `pointer-leave` or `blur` clears them.

**Press.** `press-start` on the trigger closes the tooltip and clears both signals. This follows React Spectrum S2, where any key down or pointer down on the trigger closes it (`shouldCloseOnPress`, default true); Spectrum Web Components has no press close. The web bindings do not map Enter or Space to `press-start` for the role `tooltip`: those keys belong to the trigger's own role (a button, a link), and the adapter sends the trigger's `press-start` to the tooltip too. This is a known divergence from S2, where every key down closes it. `press-start` clears `hovered` but the pointer is still over the trigger, so a `pointer-enter` that follows a hover and a `press-start` with no `pointer-leave` between them reopens the tooltip; a real adapter never sends that sequence.

**Adapter-owned**, because a contract has no clock and each is not a finite state:

* **The delays.** The warmup before a hovered tooltip shows (React Spectrum S2 1500 ms, `delay`; Spectrum Web Components `delayed`), the cooldown before a left tooltip hides (S2 500 ms, `closeDelay`; Web Components 300 ms) and the global warmup (once one tooltip has shown, the next shows without delay until a cooldown has passed). The adapter applies them before it sends `pointer-enter` and `pointer-leave`: `pointer-enter` means the pointer has rested on the trigger or the tooltip for the warmup (or none, while warm), and `pointer-leave` that it has been off both for the close delay. A pointer that leaves before the warmup ends sends neither. Keyboard focus is never delayed. Moving the pointer from the trigger onto the tooltip sends no `pointer-leave`, so the tooltip stays open (React Spectrum S2 and Web Components both do this, and it satisfies the hoverable part of WCAG 1.4.13). A pending timer is cancelled by `dismiss` and `press-start`.
* **One open tooltip at a time.** The adapter sends `dismiss` to every other open tooltip when one opens (the `change` with `isOpen: true` is the cue).
* **`aria-describedby`.** While the facet `open` is `true` the trigger has `aria-describedby` pointing at the tooltip, and has none while it is `false` (both implementations). The attribute is on the trigger, which is not an anatomy part of Tooltip, so `semantics` cannot express it yet (the same gap as `aria-labelledby`: there is no way to reference another part or element). It is documented here and in the `open` facet's description, and not covered by a vector.
* **Disabled while open.** An adapter closes an open tooltip when `isDisabled` becomes `true`, because an option changing is not an intent (React Aria `useHover` ends a hover when `isDisabled` flips to true). The contract adds no transition for it.
* **Controlled and initial state.** `isOpen` is the state; a controlled adapter treats `change` as its `onOpenChange` and may refuse it. `defaultOpen` is only the initial `isOpen`.
* **Left out of the contract.** Placement, flipping, offset and the popover (phase 5); a focus-only trigger (`trigger: focus`); `shouldCloseOnPress: false`.

### `blocksInteraction`

A registered facet may list `blocksInteraction`: the event intents that do nothing while the facet is `true`. `disabled` lists `focus`, `press-start` and `pointer-enter`: a disabled control takes no focus, press or hover. `activate` stays an explicit transition guard, as in the Switch example, because a read-only control keeps focus and ignores only activation.

## Facets in recipes

A recipe `when` or `visibleWhen` may carry `facets: { "<facet>": "<value>" }` beside `options` and `states` (`component-visual.schema.json`). It is opt-in and additive: when a recipe compiles, each facet clause folds into the `options` (a state-group facet: the option values its contract maps to that value) and `states` (an interaction facet selected as `"true"`: its `stateName`, for example `hovered` to `hover`) that the solver already reads, so no recipe that omits `facets` changes and a recipe that uses it compiles to the same output as its option form. A facet that cannot be selected never matches, and SPEC-122 warns: no contract, a facet the contract does not declare, an interaction facet no extended pattern publishes, a value the facet lacks, `"false"` on an interaction facet (a recipe cannot test a state's absence), or a value that overlaps an earlier one under first match wins. A facet clause counts as one satisfied condition per option it folds into when conditions are ranked.

## Exemptions

A component that takes no interaction has no contract. [`registry/behavior-exemptions.json`](registry.md#behavior-contract-registries) lists each one by component name with a `reason` from [`registry/exemption-reasons.json`](registry.md#behavior-contract-registries):

| Reason           | Meaning                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------- |
| `static-text`    | Text that is read, not operated (heading, body, label, help text).                          |
| `static-display` | Presents information or an image and takes no input (badge, status light, avatar, divider). |
| `container`      | Lays out, groups or wraps other components; behavior lives in what it contains.             |
| `sub-part`       | Part of another component, covered by the parent's contract (a color handle).               |
| `decorative`     | Visual embellishment with no meaning for assistive technology.                              |

An exemption is a claim about interaction, not a permanent one: if a platform makes an exempt component pressable or selectable (a selectable thumbnail in a collection), remove the entry and write a contract. A component with an `accessibility.role` reaches its contract through the role and needs no entry. Every other component has a contract or an exemption, never both (SPEC-123).

## Key bindings

A contract names intents, never keys (principle 12). Which key raises which intent is a **per-platform binding**, one file per platform, keyed by `role` (the `role` of a contract part): `behaviors/bindings/<platform>.json`, shaped by [`behavior-bindings.schema.json`](../schemas/behavior-bindings.schema.json). `web` is the only file today. A platform extension may own its file later.

```json
{
  "platform": "web",
  "capabilities": ["pointer-hover", "keyboard", "assistive-activation"],
  "roles": {
    "switch": { "keyboard": [{ "key": "Space", "down": "press-start", "up": "press-end" }] },
    "checkbox": { "keyboard": [{ "key": "Space", "down": "press-start", "up": "press-end" }] }
  }
}
```

* A `keyboard` entry maps one `key` to the event intents (one, or a list in order) it raises on `down` and on `up`. They are the existing press intents, so Space on key up and Enter on key down are both expressible. Timing is `down` and `up` only; key repeat is not a phase. Key names are a fixed list (`Space`, `Enter`, `Escape`, `Tab`, the arrows, `Home`, `End`, `PageUp`, `PageDown`) in the schema. Arrow keys are physical: right-to-left mirroring stays in the `navigate-*` intents.
* A key name is the logical name of the key, not the DOM string. A DOM adapter maps `KeyboardEvent.key` to it: `" "` to `Space`, `Enter`, `Escape`, `Tab`, `Home`, `End`, `PageUp` and `PageDown` to themselves, `ArrowUp`, `ArrowDown`, `ArrowLeft` and `ArrowRight` to themselves (physical direction). Names are case-sensitive, and a single-character key such as `a` is not a name yet. A binding matches the bare key only (decision A544): a key pressed with any modifier (Shift, Control, Alt, Meta) never matches a binding, so Shift+Space does not toggle. A binding has no modifier field, and an `input` step carries none, so the runner has nothing to test; a DOM adapter must drop modified key events before it looks up a binding. Other platforms map their own key events the same way.
* A file holds only entries that were verified against an implementation. A role with no entry has no key binding on that platform; a platform with no keyboard omits `keyboard` from `capabilities` and binds no keys. Touch and assistive entries for other platforms are added when a platform owner supplies verified ones.
* **Web, button:** Enter raises `press-start` and `press-end` on key down (decision A538: native `<button>`, React Spectrum S2 and Spectrum Web Components fire the click on key down); Space raises `press-start` on key down and `press-end` on key up. React Spectrum S2 fires its `onPress` callback on key up for Enter; that is not the DOM click, which is the behavior bound here. A held Enter repeats the click in all three, a held Space does not; repeat is not a phase (decision A541), the measured behavior is in the evidence table of proposal 022.
* **Web, radio and radio group:** on the `radio`, Space selects on key up and Enter does nothing. On the `radiogroup`, ArrowDown and ArrowRight raise `navigate-next` and ArrowUp and ArrowLeft raise `navigate-previous`, on key down; the group's `collection` moves the focus, skips a disabled radio, wraps and selects on arrival. There is no Home or End entry (decision A539). All four arrows are listed because Up and Down move in a horizontal group and Left and Right in a vertical one; the Left and Right swap is the group's `traversal.mirror` (guard `arrowOrder` is `mirrored`), which the runner applies before the lookup and an adapter applies the same way.
* **Web, Switch and Checkbox:** Space toggles, on key up; Enter does not (decision A520). The same holds for the native input, React Spectrum S2, `@ui-sdk/react` and Spectrum Web Components generation 1, as measured by the vector spike.
* **Key vectors** are per platform and role, at `conformance/behavior/bindings/<platform>/<role>.json` (`{ "platform", "role", "vectors" }`), and run against every component whose role-carrying part has that role. A component suite carries a key vector only to override its role's binding. A suite with `"item": true` (`<role>.item.json`) runs against every component whose collection item contract has a part with that role, whatever role the group itself has (Accordion's group has none and its header is a `button`); its vectors start `items` and address them with `input.item`. A step is `{ "input": { "key", "phase" } }`. The runner takes the role of the contract's role-carrying part (for an item suite, of the item contract's part, and an `input` step with `item` addresses that item), finds the entries for the key, runs the `down` or `up` intents as steps `via` the keyboard, and does nothing when no entry matches: "Enter does not toggle" is a vector that expects `emit: []`. Key vectors need `keyboard`, so on a platform without it they are not applicable.
* `design-data behavior test <component|--all> [--platform <id>]`: with `--platform` the run has that platform's capabilities (and its key vectors only); without it every platform's key vectors run with that platform's bindings.
* **SPEC-124** `behavior-bindings-well-formed`: a bindings file lists registered capabilities, binds keys only with `keyboard`, and names registered intents that a contract with that role handles.

## Reference runner

`design-data behavior test <component|--all>` runs each conformance vector in `conformance/behavior/<component>.json` (`{ "component", "vectors" }`, the shape of a contract with only `vectors`) against `behaviors/<component>.json`, with no browser. Library function: `design_data_core::behavior::run_dir`. The run has all capabilities unless `--without <capability>` removes one; a vector that needs a missing capability is **not applicable**, neither pass nor fail. The exit code is 1 when any vector fails. Rules the runner applies:

* Options are the state; a missing option reads as `false`. A facet is the first `values` entry that matches.
* An intent fires the first transition for it, in the contract and then in the patterns it extends, whose `via` equals the step's `via` (when the transition has one), whose `needs` the run has and whose `guard` holds, reading the facets from before the step. What the event intents do is the `interactive` pattern's transitions (see Patterns), not code. An intent that no transition, `handles` entry or event intent covers fails the vector.
* **Pins.** No vector can see a part's `focus`, the contract's `state` list or an unbound `role`: focus is not an intent, an option no facet reads is not observable, and a role that has no binding only drops the shared key vectors. A component suite therefore carries `pins`: `{ "state": [...], "parts": { "<part>": { "role", "focus", "press", "handles" } } }`, the `state` list and every part's fields as the suite holds them true (after the contract is flattened with its patterns). The runner reports a failing `(pins)` result for the component when the contract differs (a changed `focus`, a dropped `isDisabled`, a mistyped or removed `role`), when a part is not pinned, and when the suite has no `pins` while the contract has parts or state. The pins also hold the contract's `wcag`. A passing check adds no result, so a suite's vector count is its vectors. Pins are a change detector: they catch an accidental edit of one side (the contract or the suite), not a deliberate edit of both, which is the point of having to make it twice. The runner also fails a contract whose facet derives from an option, or whose transition changes one, that `state` does not list.
* **Unbound roles.** An `input` step whose role has no entry in the platform's bindings fails the vector, and a key suite for a role the platform's bindings lack fails the run, except on a platform with no `keyboard` capability, which binds no keys and still reports its key vectors as not applicable. A mistyped role does not skip key vectors silently: the pins (and the step error) report it.

## Spec sheet derivation

The Figma spec sheet's accessibility section reads role, focus, keyboard intents and WCAG criteria from the contract when the component has one (`design-data spec-sheet`); otherwise from the `accessibility` block. Role is the role of the only part that has one; focus is `true` when any part is a `tab-stop` and `false` when every part is `none` (`roving` is not derivable); keyboard intents are the non-event intents of the transitions, then each part's `press` and `handles`; `wcag` is the contract's list. A field the contract cannot answer exactly keeps the block's value. The component-level `intents` labels (`choose`) have no contract field, so they still come from the block. For every component with a contract that has an `accessibility` block the section built from the contract is equal to the one built from the block (a unit test over a list of components proves it), so sheets are unchanged. Radio button's `roving` focus is the one field the contract cannot answer, so `focusable` stays the block's.

## Where each `accessibility` field goes

| `accessibility` field                                 | Home in the contract                                                                                                                                                                                                             |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `role`                                                | `parts.<part>.role`. Which part carries a component-level role is decided per component.                                                                                                                                         |
| `focusable`                                           | `parts.<part>.focus`: `true` is `tab-stop`, `false` with roving focus is `roving`, `false` otherwise is `none`.                                                                                                                  |
| `wcag`                                                | `wcag`, on the contract, a facet or a part.                                                                                                                                                                                      |
| `keyboardIntents`                                     | `transitions[].on` and `parts.<part>.press` when the intent changes state; `parts.<part>.handles` when it changes none (for example `navigate-items`).                                                                           |
| `intents`                                             | **No home.** These label what a component is for (`trigger`, `choose`); no contract field says so. Open question.                                                                                                                |
| state `announce`, `communicates`, `blocksInteraction` | `communicates` overlaps `semantics`; `blocksInteraction` is a facet property in `registry/facets.json` (see `blocksInteraction`); `announce` is dropped. No component data sets any of them, so only the schema and docs change. |

## Expand, migrate, contract

1. **Expand.** The schema, the facet, intent and capability registries, patterns, the reference runner and the warnings below exist. The `accessibility` block stays; nothing reads the contract at render time.
2. **Migrate.** A component gains `behaviors/<component>.json` carrying everything its `accessibility` block says, per the table above. Both forms coexist, and renders and spec sheets stay byte-identical. Recipes then move from options to facets in their `when` clauses, per component.
3. **Contract.** When every component has a contract or a registered exemption, the `accessibility` block is removed from the schema and the data, and the SPEC-118 to SPEC-120, SPEC-122 and SPEC-123 warnings become errors, per component at zero.

## Validation

The schema shape is checked by `design-data:validate-behaviors` (AJV), which also checks the conformance baseline, as `validate-visuals` does for recipes. The SDK loads `behaviors/` (a sibling of `visuals/`, so a dataset without the directory is valid) and runs these rules, all **warnings** until components migrate:

* **SPEC-118** `behavior-references-resolve`: the component, `state` options, facets, parts, semantics and `collection` (slot, item, facet references) resolve.
* **SPEC-119** `behavior-transitions-well-formed`: intents, capabilities, guards, `do` (including `choose`) and the `collection` traversal guards resolve.
* **SPEC-120** `behavior-vectors-well-formed`: a vector's component, capabilities, steps, start options (and a group's item options, indices and expected item facets) and expectations resolve.
* **SPEC-122** `recipe-facets-resolve`: a recipe `facets` clause names a facet its component's contract can publish, with a value options or a state can select.
* **SPEC-123** `component-has-contract-or-exemption`: a component with no `accessibility.role` has a contract or a registered exemption, not both, and an exemption's reason is registered.
* **SPEC-124** `behavior-bindings-well-formed`: a platform's key bindings list registered capabilities, bind keys only with `keyboard`, and name registered intents that a contract with that role handles.
